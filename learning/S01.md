This is the "explain it to me so I can explain it to a judge" note for stage 1.
It covers the vocabulary (CVE/CWE/CVSS/EPSS/KEV/ATT&CK), why reachability is a

## 1. CVE vs CWE vs CVSS vs EPSS vs KEV vs ATT&CK

These sound interchangeable. They answer **different questions**, and that's the
whole reason Reachable exists.

| Thing | Answers | Shape |
|---|---|---|
| **CVE** | *Which specific flaw?* | An id: `CVE-2021-44228` |
| **CWE** | *What class of bug?* | An id: `CWE-502` (unsafe deserialization) |
| **CVSS** | *How bad if exploited?* | A score 0–10 + a vector |
| **EPSS** | *How likely to be exploited soon?* | A probability 0–1 |
| **KEV** | *Is it being exploited right now?* | A yes/no flag (CISA) |
| **ATT&CK** | *What technique is the attacker using?* | An id: `T1190` |

### Worked example — Log4Shell (real, from our snapshot)

`CVE-2021-44228` in Apache Log4j. From `snapshot/cves.json`:

```
cvss = 10.0          AV = NETWORK   PR = NONE   UI = NONE
epss = 0.99999 (percentile 1.0)
kev  = true          ransomware = true
cwes = CWE-20, CWE-400, CWE-502, CWE-917
```

- **CWE-502** tells you the *class*: unsafe deserialization. Same root cause as
  a hundred other CVEs.
- **CVSS 10.0** says *if* exploited, total compromise, over the network, no
  privileges, no user click.
- **EPSS 0.99999** says attackers are almost certainly using it.
- **KEV = true** says CISA has *confirmed* real-world exploitation — this isn't
  a prediction any more.
- **ATT&CK**: exploiting a Log4j endpoint from the internet is technique
  **T1190 — Exploit Public-Facing Application**, in the **Initial Access** tactic.

### Why CVSS alone misranks risk

A scanner dumps thousands of findings and sorts by CVSS. You get a wall of
"CRITICAL 9.8"s. But CVSS measures *severity in a vacuum*, not risk to **your**
environment. Two 9.8s are not equal:

- a 9.8 on an **internet-facing** box with **EPSS 0.99** and **KEV=true**, that
  sits one hop from your customer database, versus
- a 9.8 on a host in an **isolated** subnet with **EPSS 0.02**, that an attacker
  can't even reach.

CVSS scores them identically. EPSS/KEV add "is anyone actually using this?", and
— the part Reachable owns — **reachability** adds "can an attacker get here, and
does getting here lead anywhere that matters?" That last question is a graph
question.

## 2. Attack graphs — why reachability is a graph problem

An attacker doesn't care about a list of findings. They care about a **chain**:
*from the internet, can I string together steps that end at something valuable?*

Each step is one of our **attack rules** (`packages/core/attack_rules.py`). In
plain English:

- `exploit_public_facing` (T1190): the internet can pop an exposed box that runs
  vulnerable software, if no control blocks it.
- `exploit_remote_service` (T1210): from a box you own, pop another box you can
  *reach on the network* that's also vulnerable.
- `creds_in_files` (T1552.001): a box you own has secrets lying on it — take them.
- `ssh_with_stolen_key` (T1021.004): a stolen SSH key unlocks another box.
- `instance_metadata` (T1552.005): a cloud box hands you its IAM role via the
  metadata service.
- `use_cloud_account` (T1078.004): having a role/key, you use its permissions
  (and assume further roles).
- `read_cloud_storage` (T1530): a role that can read a bucket reads the bucket.
- `db_with_password` (T1078): a DB password unlocks the database.
- `local_privesc` (T1068): a local bug makes you root — needed before you can
  read root-owned secrets.

A tiny path (our `easy_web_db` template):

```
                exploit_public_facing      exploit_remote_service
   (Internet) ───────────────────────▶ (web) ───────────────────▶ (db host)
                     T1190                        T1210                │
                                                      creds_in_files   │ T1552.001
                                                                       ▼
                                                                  (db_password)
                                                      db_with_password │ T1078
                                                                       ▼
                                                              (CUSTOMER DB) ★ crown jewel
```

The question "is this finding dangerous?" becomes "**does a path from `Internet`
to a crown jewel run through this finding?**" — a reachability query on a graph.
That's why FalkorDB is the right datastore: the question *is* a traversal.

## 3. Max-flow / min-cut — the minimum set of fixes

Suppose there are 6 paths from the internet to your crown jewels. You can't fix
everything. **Which smallest set of fixes kills all 6 paths at once?**

That's a classic **min-cut**: the fewest edges to remove to disconnect a source
(`Internet`) from a sink (the crown jewels). By the max-flow / min-cut theorem,
the size of that smallest cut equals the maximum "flow" from source to sink — so
we can compute it exactly with a standard max-flow algorithm (we use networkx in
the oracle, `packages/orggen/oracle.py`).

### Why node-splitting

A naive min-cut cuts **edges**. But a defender doesn't remediate an edge — they
remediate a **finding or a step** (patch a CVE, remove a secret, tighten a role).
One finding can enable *several* edges (e.g. the same vulnerable DB is reachable
from three different front-ends). We want the cut to count that finding **once**.

**Node-splitting** does exactly that. For every fix token `t`, we split it into
`t_in → t_out` with **capacity 1**, and route every attack edge that fix enables
*through* that one pair (with infinite capacity on the attack edges themselves):

```
   ...→ t_in ──cap 1──▶ t_out →...     cutting this one unit removes
   ...→ t_in              t_out →...     EVERY edge the fix enables
```

Now the min cut can only ever cut capacity-1 fix edges, so **the cut is a set of
fixes**, and a fix shared by many attack edges costs 1, not many. The result is
the minimum remediation set. The test
`test_min_cut_removal_disconnects_all_crown_jewels` proves it: remove the cut,
recompute, and no crown jewel is reachable.

## 4. Schema decisions — node vs property vs edge

The rule of thumb: **it's a node if you traverse *to* it or attach things to it;
a property if it only describes its owner; an edge if it's a relationship you
traverse.** Three choices from our schema:

1. **`Vuln` is a node, not a property of `Software`.** A vuln is a thing findings
   point at (`Finding-[:OF]->Vuln`), software has (`Software-[:HAS_VULN]->Vuln`),
   and controls mitigate (`Control-[:MITIGATES]->Vuln`). Three different
   relationships converge on it — that's a node, not a string field.

2. **`CAN_REACH` is an edge derived from rules modelled as data.** We don't
   hand-draw "web can reach db". We store firewall/security-group rules
   (`ReachRule`: zone→zone→port) as data and *derive* the `CAN_REACH` edges from
   them. That mirrors reality (you write rules; reachability falls out) and lets
   a reviewer explain *why* X reaches Y: "because a rule allows that zone pair on
   that port." The attack step `exploit_remote_service` then rides those edges.

3. **`Vuln` is DENORMALISED into each org graph** — and this is the key FalkorDB
   decision. The canonical CVE lives once in the `threatintel` graph. But
   FalkorDB (like Redis) keeps every graph separate: **a Cypher query cannot JOIN
   across two graphs.** An attack-path traversal needs `cvss`/`epss`/`kev`/`av`
   *right next to* the `Software` it sits on, in the *same* graph, or every hop
   would need an out-of-band lookup and the traversal would fall apart. So we
   copy the handful of fields the rules read onto a `Vuln` node inside each org
   graph, keeping `cve` as the link back to the canonical record. Denormalisation
   is normally a smell; here it's forced by the "one query, one graph" boundary
   and it's the right call.

A scoping note: **`MITIGATES` is scoped to an asset.** A patch/WAF protects a
*specific* host, not the CVE everywhere. We put the scope on the edge
(`MITIGATES {asset: <asset id>}`), so a step only counts as blocked when the
compromised asset matches. Clean, and the oracle reads the same scope.

## 5. Five Cypher queries to run NOW (FalkorDB Browser → http://localhost:3001)

Pick graph `org_a` for 1–4, `threatintel` for 5. All are parameter-free so you
can paste them straight in.

**(1) Internet entry points — exposed assets running a serious network vuln:**
```cypher
MATCH (:Internet)-[:EXPOSES]->(a:Asset)-[:RUNS]->(:Software)-[:HAS_VULN]->(v:Vuln)
WHERE v.av IN ['NETWORK','ADJACENT_NETWORK'] AND v.cvss >= 7.0
RETURN a.hostname, v.cve, v.cvss
ORDER BY v.cvss DESC LIMIT 5;
```

**(2) A planted attack path, hop by hop (the `easy_web_db` shape):**
```cypher
MATCH p = (:Internet)-[:EXPOSES]->(:Asset)-[:CAN_REACH]->(:Asset)
          -[:HOLDS]->(:Secret)-[:UNLOCKS]->(d:DataStore {crown_jewel: true})
RETURN [n IN nodes(p) | coalesce(n.hostname, n.kind, n.id)] AS hops
LIMIT 1;
```

**(3) A severity decoy — a CRITICAL + KEV vuln the Internet can't reach:**
```cypher
MATCH (a:Asset)-[:RUNS]->(:Software)-[:HAS_VULN]->(v:Vuln)
WHERE v.cvss >= 9.0 AND v.kev = true
  AND NOT ( (:Internet)-[:EXPOSES]->(a) )
  AND NOT ( ()-[:CAN_REACH]->(a) )
RETURN a.hostname, v.cve, v.cvss LIMIT 5;
```
These are the findings a CVSS-only tool screams about but an attacker can't
touch. Compare against query (1).

**(4) A mitigated finding — a vuln blocked by a control on its own asset:**
```cypher
MATCH (c:Control)-[m:MITIGATES]->(v:Vuln)<-[:HAS_VULN]-(:Software)<-[:RUNS]-(a:Asset)
WHERE m.asset = a.id
RETURN a.hostname, v.cve, c.kind LIMIT 5;
```

**(5) A KEV vuln and the ATT&CK technique for exploiting a public-facing app
(graph `threatintel`):**
```cypher
// The technique + tactic our exploit_public_facing rule maps to:
MATCH (t:Technique {id: 'T1190'})-[:IN_TACTIC]->(tac:Tactic)
RETURN t.id, t.name, tac.name;
// ...and some ransomware-associated KEV CVEs in the snapshot:
MATCH (c:CVE) WHERE c.kev = true AND c.kev_ransomware = true
RETURN c.id, c.cvss ORDER BY c.cvss DESC LIMIT 5;
```

## 6. Explain it to a judge (3 Q&As)

**Q: What does Reachable actually do that a scanner doesn't?**
A scanner gives you a sorted list of CVEs. Reachable puts your infrastructure in
a graph next to real threat intel and asks a different question: *from the
internet, what can an attacker actually reach, and which findings lie on a real
path to something valuable?* A critical CVE with no path to anything is noise; a
medium CVE that's the first hop to the customer database is the real emergency.
We rank by reachability, not by CVSS.

**Q: Why FalkorDB and not Postgres?**
Because the core question is a multi-hop traversal — "is there a path from
`Internet` to a crown jewel through these steps?" — and that's native to a graph
database and awkward as recursive SQL joins. FalkorDB does the real work: the
attack graph, the path queries, the min-cut. We keep a Postgres mirror only to
*prove* that later, by benchmarking the same query both ways.

**Q: How do you know your attack paths are correct and not made up?**
Two independent implementations of the same rule spec have to agree. The
generator plants ground-truth paths; a separate pure-Python oracle (networkx)
rebuilds the attack graph from the *same* rules and must rediscover every planted
path, must never route through a decoy, and its min-cut must actually disconnect
the crown jewels when removed. All of that is enforced by the test suite. When S2
derives the paths in Cypher, it's graded against this same oracle — so "the graph
says so" is always checkable against an independent answer key.
