# S03 -- The company brain and the agent's memory (for Atharv)

S02 made the graph answer *attacker* questions. S03 makes it answer the two
other kinds of question a security team asks every day:

* **Organisational** (Track 03): *who owns this, who's on call, why is this port
  open, who signed off on it, did we fix something like this before?*
* **Memory** (Track 02): *what did we decide about this finding last time, is
  that decision still valid, what keeps happening, and how do we handle this
  technique?*

Both live **in the same org graph** as the infrastructure. That is the whole
idea of this session, and section 3 explains why it matters.

Before that, two fixes that make the S02 results honest (section 1), and the
graph change that makes min-cut worth demoing (section 2).

---

## 1. A fixed finding must stop being an attack step

S02's derivation matched `(f:Finding)-[:ON]->(dst), (f)-[:OF]->(v)` and never
looked at `f.status`. So a finding the team had already patched still produced
an `ATTACK_STEP`, and the attack paths never shrank. Drift detection (S5) would
have been meaningless: "you fixed it, the path is still there".

The fix is one predicate in the three exploit rules:

```cypher
WHERE v.av IN $network_vectors AND f.status = $open_status
```

and the same filter in the oracle (`_Index.finding_by` only maps OPEN
findings). The constant `OPEN_STATUS = "open"` lives in `attack_rules.py`, the
one spec both implementations read, so they cannot disagree about it.

A fixed finding stays in the graph: it is history (a closed `Ticket` points at
it, section 3). It just enables nothing.

**How we know it works.** Scan v2 (`drift_org`) now patches the entry finding
of the planted `easy_web_db` path, plus 20 background findings, and opens one
new path. The test `test_status_filter_v1_unchanged_v2_shrinks` derives both
scans in FalkorDB and asserts:

```
v2 paths == { v1 paths that use no fixed finding }  +  { the one new path }
```

exactly, and that no `ATTACK_STEP` anywhere has a fixed finding as its fix token.

| org | v1 paths | v2 paths, old code (no filter) | v2 paths, now |
|---|---|---|---|
| org_a | 9 | 10 (patched path still counted) | 9 (-1 patched, +1 new) |
| org_b | 4 | 5 | 4 |
| org_c | 6 | 7 | 6 |

Writing that test found a second bug: drift's "new findings" sometimes landed
on planted software and duplicated an existing (host, CVE) finding. A rescan
reports one finding per host and CVE, so drift now only adds genuinely new CVEs
on background software.

## 2. Shared infrastructure: why min-cut now has something to say

In S02 every planted path was an isolated spine of fresh nodes. Paths shared
nothing but the crown jewel, so the minimum cut was always "one fix per path"
and `choke_points` had nothing to converge on. Real companies have funnels.

| org | funnel planted | paths | min-cut before | min-cut after |
|---|---|---|---|---|
| org_a | one CI runner that three internet-facing services can call; it holds the deploy cloud key | 6 -> 9 | 6 | **7** |
| org_b | a legacy admin jump host both DMZ web servers can reach, holding a crown DB password, but **a WAF blocks it** | 4 -> 4 | 4 | 4 |
| org_c | the vendor VPN gateway is the shared entry of two routes (on-prem exploit; vendor SSH key) | 4 -> 6 | 4 | **5** |

On org_a, patching the runner is one fix that kills three paths: 9 paths, 7
fixes. `choke_points` now puts the runner first (on 3 of 9 crown paths), and on
org_c the gateway (2 of 6).

**Why org_b's funnel is blocked.** You might want a third funnel org where the
cut still equals the path count. That is impossible, and the reason is worth
knowing. If two paths `p1 -> X -> p2` and `q1 -> X -> q2` share a node X, the
graph also contains `p1 -> X -> q2` and `q1 -> X -> p2`: at least 4 paths, yet
cutting `p1` and `q1` (2 fixes) kills all of them. Sharing a node *always*
makes the cut smaller than the path count. So the contrast org has the funnel
on the **network** (both web servers can reach the jump host) but a Control
blocks the jump host's vuln, so no **attack** path crosses it. That is also a
nice demo line: "this control is the only reason org_b doesn't look like org_a".

The oracle and the Cypher min-cut still agree exactly (`prefer="crown"` gives
the oracle's set on every org; `test_min_cut_matches_oracle_on_shared_infra`),
and on the funnel orgs the shared hop's own fix is in the entry-side cut.
`labels.json` lists each funnel under `shared_infra`.

## 3. A knowledge graph built from "documents"

### 3.1 The documents, and what they become

In a real company the organisational truth is scattered: a CODEOWNERS file, an
on-call spreadsheet, ADRs in a wiki, tickets in Jira. Each one is a document,
and each one is really a handful of **facts about things the security graph
already contains**. Turning them into a knowledge graph means pulling out those
facts and attaching them to the right nodes:

| document | nodes | edges |
|---|---|---|
| CODEOWNERS / service catalogue | `Team {id, name, change_effort}` | `(Team)-[:OWNS]->(Asset \| DataStore)` |
| team page | `Person {id, name, role}` | `(Person)-[:MEMBER_OF]->(Team)` |
| on-call rota | `OnCall {id, window, start, end, current}` | `(OnCall)-[:FOR]->(Team)`, `(Person)-[:ON_CALL]->(OnCall)` |
| ADR | `ADR {id, title, decision, date, port, cidr}` | `(ADR)-[:CHANGED]->(Asset)`, `(ADR)-[:APPROVED_BY]->(Person)` |
| ticket | `Ticket {id, title, status, opened, closed}` | `(Ticket)-[:FIXES]->(Finding)` |

The S01 rule of thumb still decides node vs property: **a node if you traverse
to it or hang things off it; a property if it only describes its owner.**

* The ADR is a **node**, not a text field on the asset, because two different
  relationships meet on it: what it changed and who approved it. The port it
  opened is a **property**: you filter by it, you never traverse to it.
* An on-call slot is a **node**, not a `Team.on_call` property, because it has
  its own time window and its own person, and "who was on call last week" must
  stay answerable after the rota moves on. `current: true` marks the live slot,
  so "who is on call now" doesn't depend on the reader's clock (our data lives
  in a synthetic 2024; the demo runs in 2026).
* A person is a **node** because the same person approves ADRs, sits in a team
  and holds rota slots. One node, three relationships.

The generator (`packages/orggen/company.py`) plants this deliberately: an ADR
for **every planted path's internet-facing entry**, and for each funnel
("let every service call the shared CI runner", "store the vendor SSH key on
the gateway"); ticket history (four closed tickets on findings now `fixed`, two
open tickets on live findings); ownership mostly by zone, but 1 asset in 7
belongs to another team, so routing a fix is a real lookup. Names are invented
(two made-up word lists), so nobody real is in the data.

### 3.2 Why "trace a decision to its source" is one query

"Why is port 443 open on `vireo-sol-vpn-45`, and who approved it?" In a
document world that's a search across the wiki, a guess, and a Slack thread.
Here it is one traversal from the Internet through the exposure to the
decision and the person:

```cypher
MATCH (:Internet)-[x:EXPOSES]->(a:Asset {hostname: $host})
MATCH (adr:ADR)-[:CHANGED]->(a) WHERE adr.port = x.port
MATCH (adr)-[:APPROVED_BY]->(p:Person)
OPTIONAL MATCH (p)-[:MEMBER_OF]->(t:Team)
RETURN adr.id, adr.title, adr.decision, adr.date, p.name, p.role, t.name
```

`decision_trail` runs exactly this (plus the asset's live `ATTACK_STEP`s from
the Internet) and returns the ADR id in its evidence. Live, on org_c:

> 1 decision(s) on vireo-sol-vpn-45:443. Latest: ADR-005: Expose
> vireo-sol-vpn-45 on tcp/443 to the Internet (2023-09-24), approved by Brisa
> Ironvale (Head of Security, Security Office). Open 0.0.0.0/0 ->
> vireo-sol-vpn-45:443 (gateway) for site-to-site access for Lumisk Analytics.
> ... exploitable from the Internet via 1 attack step(s).

The answer **has a source**: the ADR id. A human can open it. That is what
makes the company brain trustworthy, and why the edge is better than an
embedding: similarity search would return "ADRs that look like this one"; the
edge returns *the* decision that changed *this* asset.

The negative pattern is just as useful. `NOT (:ADR)-[:CHANGED]->(a)` on an
exposed asset is an **undocumented exposure**: org_a has 32 of them (the
background exposed hosts). `decision_trail` says so instead of inventing a
reason.

### 3.3 Fixed intents, not text-to-Cypher

`company_query(org, question_kind, params)` takes one of five intents:
`who_owns`, `who_is_on_call`, `why_exposed`, `who_approved`, `fix_history`.
Each has its own Pydantic parameter model with `extra="forbid"`, so a stray
key, a Cypher string or prose is rejected before anything reaches FalkorDB.
The S4 agent's job is to map a person's words onto one intent and fill its
parameters; the query behind each intent is fixed, parameterised, read-only
and returns evidence. Same reasoning as S02's typed tools: the LLM chooses,
the graph answers.

## 4. Three kinds of memory, as nodes

An agent that forgets everything between runs re-triages the same findings
forever, contradicts last week's decision, and never learns that a problem
keeps coming back. Cognitive science splits memory three ways, and the split
maps cleanly onto our graph.

### 4.1 Episodic: what happened

```
(Run {id, started, kind})-[:HAS_STEP]->(AgentStep {id, tool, input_hash, ts, seq})
(AgentStep)-[:NEXT]->(AgentStep)
(Run)-[:HAS_TRIAGE]->(Triage {id, ts})-[:HAS_VERDICT]->(Verdict {id, decision, reason, ts})
(Verdict)-[:ON]->(Finding)
(RiskAcceptance {id, reason, approved_by, created, expires})-[:ON]->(Finding)
(RiskAcceptance)-[:APPROVED_BY]->(Person)
```

* **Steps are ordered twice**: a `seq` number (for sorting) and a `NEXT` chain
  (for traversal). `get_run` checks they agree (`chain_ok`). The append query
  computes `seq` as one past the last step and adds the `NEXT` edge in the same
  statement, using the Cypher idiom "create this edge only if there is a
  previous step": `FOREACH (p IN CASE WHEN prev IS NULL THEN [] ELSE [prev] END
  | CREATE (p)-[:NEXT]->(s))`.
* `input_hash` is the sha256 of the tool input's canonical JSON. Same input,
  same hash, regardless of key order: that's the replay key, and it lets S4
  spot an agent calling the same tool with the same arguments in a loop.
* A `Verdict` points at the **Finding**, not at a copy of it: when you look at
  a finding you see every verdict ever given on it, newest first.
* A `RiskAcceptance` has an **approver edge** to a real `Person` (the same node
  the company layer uses) and an **expiry**. It is episodic (someone decided
  something at a time) with a temporal validity (section 6).

### 4.2 Semantic: what we learned

```
(Pattern {id, kind, description, ts})-[:ABOUT]->(Asset | Software | Vuln)
(Pattern)-[:SEEN_IN]->(Triage)
```

A Pattern is a generalisation: *"the redis golden image keeps reintroducing
CVE-2022-0543: patching hosts one by one does not stick, rebuild the image."*
It is wired to a few concrete Software/Vuln nodes and to the triages where it
was noticed (its provenance).

Its **reach** is wider than its edges: `triage_memory` attaches a pattern to a
finding if the pattern is ABOUT the finding's asset, ABOUT any Software with
the same CPE (same image), or ABOUT any Vuln with the same CVE. The seeded
pattern on org_a is wired to 3 vulns but reaches 398 findings on 217 hosts.
That is the point of semantic memory: learn once, recognise everywhere.

`upsert_pattern` derives the id from `(kind, sorted entities)`, so learning the
same thing twice refreshes the node instead of duplicating it.

### 4.3 Procedural: how we handle it

```
(Technique {id})-[:HANDLED_BY]->(Playbook {id, technique, version, body, ts})
(Playbook)-[:SUPERSEDES]->(Playbook)
```

A playbook is "how to handle T1190". Procedures change, and you want to know
which procedure was in force when a decision was made, so a new version is a
**new node** that `SUPERSEDES` the old one. Nothing is overwritten. The
current playbook is the one nothing supersedes:

```cypher
MATCH (:Technique {id: $t})-[:HANDLED_BY]->(p:Playbook)
WHERE NOT (:Playbook)-[:SUPERSEDES]->(p)
```

Version ids are deterministic (`<org>:playbook:T1190:v3`), so two agents that
both read v2 as current and both try to publish v3 collide on `MERGE`: the
loser sees `nodes_created == 0` and gets an error instead of silently forking
the history (`test_playbook_version_race_is_detected`).

`Technique` here is an org-local anchor node with the ATT&CK id. The canonical
technique lives in the `threatintel` graph, but graphs can't be joined (S01),
so we keep the same denormalisation trade-off as `Vuln`.

## 5. Why memory lives in the graph, and why handoffs go through a Run

**Coordination.** In S4 several agents (triage, remediation, drift) work on the
same org. If memory lived in each agent's context window, agent B would know
nothing of agent A's verdicts. With memory as nodes on the Finding, every agent
that looks at the finding sees them, through the same tool, with no message
passing.

**Handoff = "continue Run X".** The Run node is the shared workspace: agent A
appends steps; agent B gets the run id and appends more. Order is preserved by
construction (`test_run_round_trip_keeps_step_order` hands a run to a second
writer and checks seq 0..3 with an intact NEXT chain).

**Durability.** A context window dies with the process; a node survives
restarts, and `GRAPH.COPY` / backups take it along.

**Replay and audit.** A Run with ordered steps and input hashes is a script:
you can re-execute it against the graph and check you get the same answers,
or show a judge exactly what the agent did and in what order.

**One query, both worlds.** Because memory sits next to the facts, "findings
on a crown-jewel path whose risk acceptance has expired" is a single traversal
over attack steps, findings and acceptances. Store memory in a separate vector
DB and that question becomes a join across two systems.

**Narrow writes.** These are the first runtime writes into org graphs, so they
are fenced in `reachable_graph/memory.py`:

* every write is one of the Cypher constants in `WRITE_QUERIES`; `_w` refuses
  anything else, and values only ever travel as parameters;
* writes CREATE/MERGE memory nodes and edges *from* them; they never SET or
  DELETE an infrastructure node;
* `test_memory_writes_never_touch_infrastructure` hashes every non-memory node
  and edge before and after a burst of writes of every kind, and requires the
  hash to be identical.

The tool layer stays read-only. `triage_memory` is a read (GRAPH.RO_QUERY
through `GraphTools._q`), so the S2 property test "no tool ever writes to an
org graph" still covers every tool, including the four new ones.

## 6. Time: expiry, versions, and "then vs now"

Three temporal patterns, one idea: **store when something was true, and pass
"now" in as a parameter instead of reading the clock inside the logic.**

* **Expiry as a property.** `RiskAcceptance.expires` (epoch seconds). The read
  computes `ra.expires > $now AS live` in Cypher, so "live" means one thing
  everywhere. A live acceptance suppresses its finding; an expired one is still
  returned, labelled expired, and does **not** suppress. That is the seeded
  demo: org_a's medium path entry finding has an acceptance that expired in
  December 2023. It sits on a crown-jewel path. Memory must not hide it.
* **Versioning as edges.** `SUPERSEDES` chains keep every playbook version.
  "Now" is the unsuperseded head; history is a variable-length walk down the
  chain.
* **Then vs now.** Because "now" is a parameter, the past is one argument away:
  - `triage_memory(org, findings, as_of=T)`: which acceptances were in force at
    T (the test shows the same acceptance suppressing at T and not after it
    expires);
  - `playbook_at(org, technique, T)`: the latest version published at or
    before T;
  - on-call: the `current` flag answers "now"; every slot keeps its
    `start`/`end`, so "who was on call that week" is a plain Cypher filter
    (the `owners` tool itself reports only the current slot).

Timestamps are integer epoch seconds everywhere (the S01 FalkorDB timestamp
lesson). Careful: Cypher's `timestamp()` is in **milliseconds**, so compare
`ra.expires > timestamp() / 1000`.

## 7. Stretch: capacity as effort -- "cheapest" vs "fewest" cut

`min_cut` answers "the **fewest** fixes that cut every path" by giving every
fix gate capacity 1 (S02 section 4). But fixes aren't equal. Patching a web
server is an afternoon; upgrading a vendor VPN appliance needs a maintenance
window and the vendor.

Max-flow doesn't care what the capacities mean. Give each gate a capacity equal
to its **effort** and the very same algorithm returns the cut with the lowest
**total effort**. Nothing else changes: same FLOW layer, same `algo.maxFlow`,
`capacityProperty: 'effort'` instead of `'cap'`.

**The effort model** (`reachable_core/effort.py`, a modelling choice like
`exploit_likelihood`): a finding costs what its asset kind costs (web server 1,
db host 3, CI runner 4, gateway 5); a credential/permission step costs what its
rule costs (vault a secret 2, rotate a production DB password 3, ...); plus the
owning team's `change_effort` (Build & Release is under a change freeze: +1).
Clamped to 1..5. `derive` stamps it on every gate in one Cypher pass that
reaches each gate by traversal (`(u)-[:FLOW]->(fi:FixIn)`), not by a per-row id
lookup.

**Worked example, org_c.** The VPN gateway is the shared entry of two routes.

```
                 +-- gw -> on-prem server (2) -> db password (3) -> crown
internet -(5)- gw
                 +-- gw holds vendor ssh key (2) -> mgmt server (2) -> ... -> crown
```

* fewest: cut the gateway finding. **1 fix, effort 5.**
* cheapest: cut the cheapest hop on each route: **2 fixes, effort 4.**

Across all of org_c: fewest = 5 fixes / effort 9, cheapest = **6 fixes /
effort 8**. On org_a the count stays 7 but effort drops 11 -> 8 (the runner is
expensive to touch; the deploy key's role grant is cheap). org_b is identical
either way. Both plans fully disconnect the crown jewels (proved with
`simulate_fix` in the tests).

Two details carry over from S02 and generalise:

* **Cut recovery** uses residual capacities, so the gate capacity in the
  residual graph must be the effort too (`residual_min_cut(gate_cap=...)`).
* **Self-check**: max-flow = min-cut capacity. In "fewest" that's `|cut| ==
  maxFlow`; in "cheapest" it's `sum(effort of cut) == maxFlow`. If recovery
  ever disagrees, the tool raises instead of answering.

The oracle recomputes every effort in plain Python from the same spec and runs
a weighted networkx min-cut; the test requires the gate efforts and the
cheapest-cut value to match the Cypher side.

"Fewest" is still the default: it's the right question when the bottleneck is
the number of changes you can push this week; "cheapest" is right when it's
engineering hours.

## 8. FalkorDB gotchas we hit this session (exact errors + fixes)

1. **Silent nulls after an aggregation.** In the effort query, `WITH u, tok,
   max(coalesce(t.change_effort, 0)) + CASE WHEN is_step THEN $step_effort[rule]
   ... ELSE $kind_effort[n.kind] END AS x` ran without error, but `rule`,
   `is_step` and `n` were not grouping keys, so they came through as **null**
   and every gate got the default effort (only 2s and 3s). Fix: aggregate in
   one `WITH` that lists every variable you still need as a grouping key
   (`WITH u, tok, rule, is_step, n, max(...) AS bump`), then compute in the next
   `WITH`.
2. `'old' not defined` for `MATCH ... WHERE NOT (:Playbook)-[:SUPERSEDES]->(p)
   MATCH h = (p)-[:SUPERSEDES*0..]->(old:Playbook) RETURN ... old.version`.
   Same family as S02 gotcha 2: a MATCH after a `WHERE NOT (pattern)` can't bind
   new variables. Fix: put `WITH p` between the two MATCHes.
3. Map parameters **can** be indexed by a computed key: `$kind_effort[n.kind]`
   works (we probed before relying on it), so lookup tables stay parameters
   instead of being spliced into the query text.
4. `MERGE ... ON CREATE SET ...` and `FOREACH (x IN CASE WHEN c THEN [v] ELSE
   [] END | CREATE ...)` both work, which gives atomic "create if absent" and
   "conditional edge" in one statement.
5. `SET n += $map` silently skips null values (FalkorDB drops a property set to
   null), which is what we want for optional fields (an ADR without a port, an
   open ticket without `closed`), but means "property missing" and "null" look
   the same on read.
6. `timestamp()` returns **milliseconds**; our data is epoch seconds.

## 9. Five FalkorDB Browser queries (http://localhost:3001, graph `org_a`)

Run `make seed derive` first. All parameter-free.

**(1) Who owns the shared CI runner, and who is on call right now:**
```cypher
MATCH (a:Asset {kind: 'ci_runner'})<-[:CHANGED]-(:ADR)
MATCH (t:Team)-[:OWNS]->(a)
MATCH (p:Person)-[:MEMBER_OF]->(t)
OPTIONAL MATCH (p)-[:ON_CALL]->(oc:OnCall {current: true})
RETURN a.hostname, t.name, p.name, p.role, oc IS NOT NULL AS on_call_now
```

**(2) The decision trail behind each internet exposure (and the undocumented ones):**
```cypher
MATCH (:Internet)-[x:EXPOSES]->(a:Asset)<-[:CHANGED]-(adr:ADR)-[:APPROVED_BY]->(p:Person)
WHERE adr.port = x.port
RETURN a.hostname, x.port, adr.title, p.name, p.role
ORDER BY adr.date LIMIT 5;

MATCH (:Internet)-[:EXPOSES]->(a:Asset)
WHERE NOT (:ADR)-[:CHANGED]->(a)
RETURN count(DISTINCT a) AS undocumented_exposures;
```

**(3) Live vs expired risk acceptances:**
```cypher
MATCH (ra:RiskAcceptance)-[:ON]->(f:Finding)-[:ON]->(a:Asset)
MATCH (ra)-[:APPROVED_BY]->(p:Person)
RETURN a.hostname, f.id, p.name, ra.expires > timestamp() / 1000 AS live, ra.reason
```
The expired one is on `larch-meadow-edge-182`, the entry of a crown-jewel path.

**(4) The current playbook for T1190, with its version history:**
```cypher
MATCH (:Technique {id: 'T1190'})-[:HANDLED_BY]->(p:Playbook)
WHERE NOT (:Playbook)-[:SUPERSEDES]->(p)
WITH p
MATCH (p)-[:SUPERSEDES*0..]->(old:Playbook)
RETURN p.version AS current, p.body, collect(old.version) AS history
```

**(5) A pattern's reach (wired to 3 vulns, reaches every finding with that CVE):**
```cypher
MATCH (pat:Pattern)-[:ABOUT]->(v:Vuln)
WITH pat, collect(DISTINCT v.cve) AS cves
MATCH (f:Finding)-[:OF]->(v2:Vuln) WHERE v2.cve IN cves
MATCH (f)-[:ON]->(a:Asset)
RETURN pat.description, count(DISTINCT f) AS findings, count(DISTINCT a) AS hosts
```

## 10. Explain it to a judge

**Q: How does Reachable answer "why is this exposed, and who approved it?"**
Decisions are part of the graph. Each architecture decision record is a node
with a `CHANGED` edge to the asset it changed and an `APPROVED_BY` edge to the
person who signed it off, and that person sits in a team. So the question is a
single traversal: Internet, exposure, asset, ADR, approver, team. The answer
cites the ADR id, so you can open the source, and it comes with what matters
for security: whether that exposure is exploitable from the Internet right now.
If there's no ADR, we say "undocumented exposure" instead of guessing; on one of
our orgs that's 32 internet-facing hosts nobody wrote down a reason for.

**Q: Your agents have memory. Why put it in the graph instead of a vector store
or the prompt?**
Because memory is about things that are already in the graph. A verdict is
about a finding; a risk acceptance is about a finding and was approved by a
person; a pattern is about a software image. As nodes and edges, every agent
sees them on the finding itself, they survive restarts, and questions mixing
memory and attack paths ("crown-jewel findings whose acceptance has expired")
are one query. We split memory into episodic (runs, verdicts, acceptances),
semantic (patterns) and procedural (versioned playbooks), and model time
explicitly: an acceptance stops suppressing at its expiry, and a playbook
change adds a version instead of overwriting one, so we can always say what was
true then and what is true now.

**Q: What does "one fix, many paths" mean, and isn't the fewest fixes always best?**
When attack paths funnel through shared infrastructure, like one CI runner
that every service can call, max-flow/min-cut finds that the single runner
patch cuts three paths at once: 9 paths, 7 fixes. But fewest isn't always
cheapest. We give every fix an effort from what it touches and who owns it, use
effort as the max-flow capacity, and the same algorithm returns the lowest-effort
plan. On our hybrid org, fewest is 5 fixes including a vendor-gateway upgrade;
cheapest is 6 easier fixes with less total effort. Both are proved to disconnect
the crown jewels before we recommend them.
