# S06 -- The frontend: a graph you can read, a stream you can watch, a key you never ship (for Atharv)

S01-S05 built a backend that can find every attack path, prove the minimum fix
set, remember last week and stream its own reasoning. None of that is visible
to a judge. S06 is the part they see: a Next.js app with seven screens, in demo
order, that all read the real graph.

The rule this session lived by: **a beautiful screen that does not show the
real path is worthless.** Every number, path, owner and ADR on screen comes
from FalkorDB through the API. The UI computes nothing a judge could doubt.

Code: `apps/web` (Next.js 16 App Router, TypeScript, Tailwind 4, shadcn/ui,
Cytoscape.js), plus three thin backend additions in `apps/api`:
`views.py` (findings board, run subgraph, fix plans), `ask.py` (English ->
fixed intent), and the run cap in `main.py`.

```bash
make up && make seed            # backend + data (once)
make web                        # http://localhost:3000 (apps/web/.env.local holds the key)
make web-test                   # proxy unit tests + build + client-bundle key scan
make e2e                        # Playwright smoke (needs the backend and one org_a v1 run)
```

## 1. Drawing an attack graph with Cytoscape

### Elements, stylesheet, layout: three separate things

Cytoscape keeps three things apart, and the separation is what makes it
fast to iterate on:

* **Elements** are plain data. A node is `{data: {id, name, kind, crown,
  paths: [0, 3], shared: 3}}`; an edge is `{data: {id, source, target,
  technique, fix_token, in_fewest, in_cheapest}}`. Our API already returns
  exactly that shape (`GET /runs/{id}/subgraph`), so the component does no
  graph logic at all: it maps JSON to elements.
* **The stylesheet** is CSS-like selectors over that data and over classes:
  `node[kind = 'secret']` is a diamond, `edge.onpath` is ember, `edge.cut` is
  white and dashed. State changes (focus a path, show the cut, simulate the
  fix) only add and remove *classes*; they never rebuild the graph or re-run
  the layout. That is why toggling "fewest / cheapest" is instant and the
  nodes do not jump.
* **The layout** decides positions once per graph.

### Why a layered (dagre) layout for an attack graph

An attack graph is "DAG-ish": every path starts at the Internet and ends at a
crown jewel, and almost every edge moves the attacker one hop further in. A
force-directed layout (cose, fcose) ignores that direction: it makes a
hairball that looks impressive and reads like nothing. A **layered** layout
(dagre, `rankDir: "LR"`) puts each node in a column by how far it is from the
Internet, so the picture reads left to right like a sentence:

```
Internet -> web server -> CI runner -> cloud key -> deploy role -> bucket
   rank 0      rank 1       rank 2       rank 3        rank 4       rank 5
```

We use `ranker: "network-simplex"` (it keeps edges short, so parallel paths
stay in parallel rows), `rankSep: 130` (room for the technique labels between
columns) and `nodeSep: 44` (two-line labels under each node). The convergence
the min cut exploits is then *visible*: three rows of web servers funnel into
one CI runner node, labelled `x3`.

### Motion that explains something

Three animations, each answering a question:

* **The path draws itself hop by hop** (`hopDepths()` does a BFS from the
  Internet; each depth fades in 230 ms after the previous one). It answers
  "how does the attacker get in?" in the order the attacker would.
* **Marching dashes** on the attack edges show the direction of travel.
* **Findings rows slide** when you flip "severity" to "reachability" (FLIP:
  measure each row's old `offsetTop`, render the new order, animate the
  difference). You watch the CVSS 5.0 climb to #1 and the 9.8s sink.

Everything respects `prefers-reduced-motion`.

### Caps, because a projector must never hang

The canvas renderer is fast; dagre and label layout are what get slow, and a
graph with hundreds of labels is unreadable anyway. So there are caps at
three levels:

1. **The API** keeps the most likely paths first until 60 nodes / 160 edges
   (`views.MAX_NODES`, `MAX_EDGES`) and reports `truncated` and
   `total_paths`, which the graph shows as "Showing 7 of 31 paths".
   A single path too large for the budget is skipped, not drawn half.
2. **"+1 hop of context"** adds at most 24 neighbouring nodes, flagged
   `context: true` and drawn faint and dashed: the path plus its
   surroundings, never the whole org.
3. **The component** hard-caps at 150 nodes whatever arrives, and skips the
   draw-in animation above 80.

### The Cytoscape gotcha that cost us a blank screen

Cytoscape injects a stylesheet that sets `position: relative` on its
container. Our container was `absolute inset-0` (fill the panel), so
Cytoscape silently overrode it, the container collapsed to **0 px high**, and
the graph reported "ready" with 29 nodes while showing nothing. Fix: an
absolutely positioned wrapper with the Cytoscape container as a `h-full
w-full` child. (Found by reading `getBoundingClientRect()` in the browser:
`{width: 1210, height: 0}`.)

## 2. Streaming a run to the browser

### Why EventSource cannot carry the API key

The backend stream (`GET /runs/{id}/stream`, S5) needs `X-API-Key`. The
browser's `EventSource` API takes a URL and one option, `withCredentials`.
**There is no way to set a request header.** The usual workarounds are all
bad here:

* put the key in the query string: it lands in browser history, proxy logs
  and the Referer header, and anyone who opens DevTools has it;
* use `fetch()` and parse the stream yourself: works, but you lose
  EventSource's automatic reconnect and `Last-Event-ID`, and the key is
  still in the browser;
* cookies: needs a login system we do not have.

### The Next proxy

The browser never talks to the backend. It talks to **its own origin**,
`/api/r/<path>`, a Next route handler (`app/api/r/[...path]/route.ts`) that
runs on the server:

```
browser                       Next (server)                    FastAPI
EventSource('/api/r/runs/X/stream')
   ----- GET, same origin --->  forward(): allowlist check,
                                add X-API-Key from server env
                                ----- GET + X-API-Key ------>   reads the trace,
                                <---- text/event-stream ------   writes events
   <---- the same bytes ------  return new Response(upstream.body)
```

`forward()` returns the upstream body as-is, so events are relayed as they
arrive, not buffered. Two headers make sure nothing in between buffers them:
`Cache-Control: no-cache, no-transform` (no-transform stops the compression
middleware from holding chunks back) and `X-Accel-Buffering: no` (for nginx).
The browser's abort signal is passed upstream, so closing the tab stops the
backend from polling the trace for a reader that is gone.

### Resuming with Last-Event-ID

Every event the backend sends has `id: <trace seq>`. When the connection
drops, EventSource reconnects by itself and sends `Last-Event-ID: 17`. The
proxy forwards that header, and the backend resumes **after step 17**. That
works because the stream reads the durable, ordered trace in the graph (S5),
not an in-memory queue. The UI also de-duplicates events by `(seq, type,
rank, finding)`, in case a reconnect lands mid-step.

### Replay is not "the stream, faster"

For the demo video we never depend on a live model. Replay mode reads a
finished run's events (`GET /runs/{id}/events`, from the graph) and plays
them back **with their real latencies**: a model call that took 6.4 s waits
6.4 s at 1x (1.6 s at 4x). The video shows the real rhythm of the run
(milliseconds in FalkorDB, seconds in the model) with no model behind it.

## 3. Keeping the API key on the server

Next.js inlines into the client bundle only env vars named `NEXT_PUBLIC_*`.
Ours is `REACHABLE_API_KEY`, read in exactly one file,
`lib/server/backend.ts`, which starts with `import "server-only"`: if any
client component ever imports it, the **build fails**. Three more rules:

* **An allowlist, not a pass-through.** The proxy forwards only the
  endpoints the UI uses (`GET orgs`, `POST orgs/{org}/ask`, ...). `/docs`,
  `/openapi.json`, `..` segments and any other method get a 404 from the
  proxy and never reach the backend.
* **No cross-site POSTs (CSRF).** A proxy that adds a key to whatever reaches
  it is a confused deputy: another site open in the same browser could
  form-post to `localhost:3000/api/r/runs` and start billed runs. So a POST
  must be `application/json` (a cross-site form cannot send that, and a
  cross-site fetch with it needs a CORS preflight this route never approves)
  and must come from our own origin (`Sec-Fetch-Site: same-origin`, or an
  `Origin` whose host is ours). Anything else is a 403 before the backend is
  called. (Flagged by an automated security review after the first cut.)
* **The browser's auth headers are dropped.** The proxy builds the upstream
  headers from scratch: a client cannot smuggle its own `Authorization`.
* **Proved two ways.** `backend.test.ts` (Vitest) checks that the key is
  injected upstream and appears in no response body or header.
  `scripts/check-client-bundle.mjs` runs after `next build` and scans all 46
  files in `.next/static` for the key's *value* and the env var's *name*. We
  planted the key in a file to check the scanner itself: it fails with
  `LEAK: ... <the key>` and exit 1.

## 4. One design decision: ember means "an attacker can get there"

The palette is graphite neutrals plus **one** strong accent, ember red
(`#ff5533`), and ember has exactly one meaning: *reachable*. Reachable
findings get an ember bar, attack-path edges are ember, the crown jewel under
threat is ember, the live indicator pulses ember. Nothing else is.

That rule forced decisions that a security UI usually gets wrong:

* **CVSS is not red.** It is a number and a grey bar. The whole product
  argues that severity is not danger, so the screen must not paint a 9.8 red
  just for being a 9.8. The quarantined Ghostcat (9.8, KEV) sits in grey,
  next to an ember CVSS 5.0.
* **KEV is a neutral outlined badge**, for the same reason.
* **The fix set is not a second colour.** Cut edges are bright white and
  dashed: the scissors, not another alarm.
* **"Safe" exists only as an outcome.** A desaturated mint appears in exactly
  one place: after a simulated fix, when the crown jewel flips from
  REACHABLE to SAFE.

The rest follows from the projector: dark (the graph glows on it), IBM Plex
Sans and Mono (wide, legible digits; tabular numerals everywhere), nothing
smaller than 12 px, and a numbered chapter nav (01 Findings ... 07 Evals)
that is the demo script.

## 5. The three backend additions

* **`POST /orgs/{org}/ask`** maps English to one of `company_query`'s five
  fixed intents. The model sees the intents as an enum and a short list of
  entities (assets with decisions, crown-path entry hosts, teams) and must
  call one function. Its choice is validated. In the first real test the
  model copied the *whole listing line* as the id; we now label the id
  (`entity_id=org_a:asset:01752 | ...`) and parse the id out of whatever
  comes back. An id it invents is rejected and the rules answer instead. In
  replay mode the rules resolver (intent keywords + word overlap) runs with
  no model at all. An honest answer beats a confident one: "why is port 22
  open on the vendor gateway" gets *"No recorded decision opens port 22 on
  vireo-sol-vpn-45; it is exposed on 443"*, then the two ADRs on record.
* **`GET /runs/{id}/subgraph`** returns the run's paths and both min cuts as
  Cytoscape elements, built from what the run wrote (PathAnalysis, FixPlan),
  so a replay shows exactly what the agents saw.
* **The run cap.** A `BoundedSemaphore(2)` taken with `acquire(blocking=False)`
  *before* the Run node is written: the third concurrent `POST /runs` gets
  `429` with `Retry-After: 30` and leaves no trace. The worker thread
  releases its slot in `finally`. Tested with a model that blocks on a gate,
  so two runs are provably in flight when the third is refused.

The findings board (`GET /orgs/{org}/findings`) needed one idea to make the
9.8-vs-5.0 moment honest rather than staged. It shows every reachable finding
plus the findings a CVSS-first team would look at instead: the scanner's own
top rows, other hosts with **the same CVE** as a reachable finding but no
path, and Internet-facing criticals that are mitigated or lead nowhere. Every
row carries its scanner rank among all 6,862 findings ("cvss #5,581") and a
one-line reason. The headline pair is chosen by rule (top of Reachable's
order vs the highest-CVSS unreachable twin of a reachable CVE, preferring a
different zone), not by id.

## 6. Gotchas (exact error + fix)

* **`redis.exceptions.ResponseError: 'e' not defined`** (FalkorDB):
  `MATCH (:Internet)-[e:ATTACK_STEP]->() MATCH (f:Finding {id: e.fix_token})`.
  FalkorDB will not use a variable from an earlier pattern inside inline
  properties. Fix: `WITH DISTINCT e.fix_token AS tok MATCH (f:Finding) WHERE
  f.id = tok`.
* **The API wedged on its first run** (Docker): `KeyError: 'litellm'` from
  `importlib._bootstrap_external._get_parent_path`, repeated inside
  `uvloop.Loop.call_exception_handler`. litellm was imported lazily inside the
  first `POST /runs` worker thread; its log filter ran on the event-loop
  thread against the half-imported package. Fix: import the agent stack on
  the main thread when the app is built (`_app()` in `main.py`). After that, 0
  KeyErrors under concurrent requests.
* **Graph "ready" but blank**: Cytoscape overrides its container's
  `position` (section 1).
* **`uvicorn --reload` on Windows** left an orphaned child holding port 8011,
  so the "restarted" server kept answering with old code. The listening PID
  belonged to no live process; the child (`multiprocessing.spawn`) had to be
  killed by command line.
* **Next 16 is not the Next you know.** `create-next-app` turns on
  `cacheComponents` + `partialPrefetching`; route segment configs like
  `export const dynamic` now error, `params` is a Promise, and anything
  reading `useSearchParams()` must sit under `<Suspense>` (ours wraps the
  whole workspace provider in the root layout). The bundled docs in
  `node_modules/next/dist/docs` are the ones to read.
* **React compiler lint** (`react-hooks/set-state-in-effect`): "reset when
  the run changes" effects became keyed components (`<PathsView
  key={runId|finding}>`) and resets inside event handlers.
* **shadcn 4 `init` is interactive** even with `-y` (it asks for a preset):
  `npx shadcn@4.21.5 init -t next -b radix -p nova -y`. It now imports `cn`
  from the `cn` package (shadcn's own, `github.com/shadcn-ui/cn`), not a
  local util.
* **A stub-model test run became what replay showed.** Replay defaults to the
  newest finished run, and a stub run is a finished run. Fix: `recent_runs`
  now returns each run's `models`; replay prefers the newest real-model run,
  and the run picker labels stub runs.
* **The free-tier pacer** (5 calls/min, S4) was dropped. A burst of 20
  concurrent Gemini calls all succeeded (paid-tier behaviour), so `llm_rpm`
  now defaults to 0; `LLM_RPM=5` brings it back. A full real v2 run now takes
  31 s, and Gate B finally shows memory saving *wall time* as well: cold
  31.8 s vs warm 21.7 s (S5 measured 66 s vs 68 s, most of it pacer waits).
  Gate A and Gate B both still pass.

## 7. Recording the demo (replay, not live)

1. `make up`, and make sure each org has one finished real-model v1 run (the
   run picker shows `· stub model` for stub runs).
2. Open `http://localhost:3000`. The top bar says **Replay**: every screen
   reads that run from the graph, the Q&A uses the rules resolver, and the
   Investigation screen plays the recorded events at 1x or 4x.
3. Demo order: 01 flip to "Sorted by severity" and back (the rows move),
   click the CVSS 5.0 headline, "See its attack path" -> 02 click a technique
   for its evidence -> 03 "Fewest fixes", point at "one fix, many paths",
   Simulate (REACHABLE -> SAFE) -> 04 Replay at 4x -> 05 org_c, the vendor
   gateway question -> 06 scan v2, the NEW CROWN PATH and what memory
   recognised -> 07 the gates.
4. The live loop (accept a risk, run v2, watch it stream) works too, but
   record it only as a separate, optional clip.

## 8. Explain it to a judge

**Q: Your findings screen puts a CVSS 5.0 above a CVSS 9.8 with a KEV badge.
Why should I trust that over the scanner?**
Because it shows its work. The 5.0 on `ember-basalt-edge-183` starts the most
likely path from the Internet to the bucket (p = 0.20): click it and you see
the five hops, and click any hop for the exact facts behind it: the finding,
the vulnerable software, the `CAN_REACH :8080` edge, the ATT&CK technique.
The 9.8 is Ghostcat on a host in the quarantine zone: nothing an attacker can
hold leads there, so patching it first changes nothing about what can be
reached. And the claim is checkable: on the fix-plan screen, simulate the
seven fixes on a copy of the graph and the bucket flips to SAFE. The 9.8 is
not among them.

**Q: Is the "live" agent feed real, or an animation?**
Both modes show real events from the run's trace in FalkorDB. Live mode
starts a run and subscribes to its Server-Sent Events through our server
(the API key never reaches your browser). Each line is a step the agents
actually took: the tool, the Cypher it ran with FalkorDB's timing, the model
call with its tokens, what memory changed. If the connection drops, the
browser reconnects and resumes from the last event it saw. Replay mode, which
we recorded the video with, plays a finished run's events from the same
trace at their real speed, so the video never depends on a model answering
mid-recording. Nothing in the feed is scripted.
