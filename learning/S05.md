# S05 -- Memory that changes behaviour, drift, and a live stream (for Atharv)

S04 gave us four agents that triage one scan. S05 is the Track 02 centrepiece:
what happens on the **next** scan. A week later the org is rescanned (scan v2:
some fixes, some new findings, one config change that opens one new path to
the crown jewel). A team that remembers does not start from scratch, and
neither should the agents. This session makes that true and *measurable*:

* the agents spend half the tokens they did (section 1);
* a **Sentinel** notices what changed between scans by diffing attack-path
  sets, not by re-triaging 7,000 findings (section 3);
* three kinds of memory each change a real decision in our runs (section 2);
* a FastAPI backend streams a run live over SSE (section 5);
* two runs can share one org graph safely (section 6);
* Gate B measures the memory lift honestly (section 7).

Code: `packages/agents/src/reachable_agents/sentinel.py` (new), `agents.py`
(recall, carried, learned patterns, playbook rules), `runtime.py` (preloads,
LLM views, trace markers), `packages/graph/src/reachable_graph/tools.py`
(`exposure_drift`, `scan_findings(view="triage")`), `memory.py` (reset,
carry-over, lock, analyst verdicts, alerts), `apps/api/src/reachable_api/main.py`,
`evals/memory_lift.py`.

The run ids quoted below are real runs on gemini-3.5-flash-lite (every LLM call
served by the primary, no fallbacks): scan v1 `org_a:run:728d232b2390`, the
analyst's verdict `org_a:verdict:fe4117af15c4`, scan v2 `org_a_v2:run:8c275ddaab63`.

## 1. The token trim: where 60k tokens went, and how we halved it

The prompt said "Triage sees raw findings". The real trace said otherwise.
Per agent, one S4 run (`org_a:run:216fc89472eb`, 60.8k input tokens):

| agent | LLM calls | input tokens |
|---|---:|---:|
| Triage | 3 | 11.1k |
| Pathfinder | 4 | 16.8k |
| Fixer | 4 | 29.7k |
| Reporter | 1 | 3.2k |

Two lessons hide in that table.

**The conversation is re-sent every turn.** A 4-turn agent pays for its first
tool result four times. Each turn also re-sends the system prompt and the tool
schemas (~5.5k characters per agent). And our JSON full of ids tokenises badly:
about **2.5 characters per token**, not the usual 4. So the cost is the turn
count times the size of what accumulates in the conversation, not the size of
any one tool result.

**The old trim was hiding data.** S4 cut every tool result to 6,000 characters
for the model by shortening lists. For `scan_findings` that meant the model saw
**6 of the 9** Internet-facing findings on crown-jewel paths, and the "... 24
more" marker. S4's "the model chose 6" was the trim choosing 6. The same cut
hid the `previously_decided` list, so the model never asked memory about the
WAF decoy and never noticed its live risk acceptance.

What we changed (each one visible in the trace):

1. **Triage works from aggregates.** `scan_findings(view="triage")` returns counts
   by CVSS band, ATT&CK technique and exposure, plus detail only for the
   *candidates* (Internet-facing findings on a crown-jewel path), a count and a
   5-row sample of the other Internet-facing ones, and the critical findings
   that enable no step. Everything else is a number, not a row.
2. **Compact views per tool** (`runtime.LLM_VIEWS`). `owners` loses the member
   list (840 to 360 characters), `decision_trail` the ADR prose, `min_cut` its
   duplicate lists, `triage_memory` the verdict history (latest decision plus a
   count). The full result is still stored as the step's `ToolOutput`. Only the
   prompt is trimmed.
3. **Brief tool descriptions.** The MCP descriptions say "USE ... Do NOT ..." for
   a host choosing among 16 tools. Our agents get 1 to 3 tools and a job that
   names them, so they get only the "what it answers" part.
4. **The run makes the calls every run makes identically**, over the same MCP
   path, traced with `by="run"`: `scan_findings`, `attack_paths` per crown jewel,
   `min_cut` in both modes, the owner/ADR lookups for the fix assets, and
   `simulate_fix` on both candidate cuts. The model keeps every *judgement*: which
   playbook, which hops to explain (`why_step`), which cut to choose, the tickets,
   and the report. S04's rule "the model chooses the tools" becomes "the model
   chooses; the run does the plumbing". Three of those were real failure
   sources, which the trace showed:
   * the Fixer simulated `fewest`, answered `cheapest`, and wrote that the
     simulation had passed (the grounding caught it: "NOT verified");
   * on another run it retyped `step:usekey:...` as `org_a:step:usekey:...`, so
     simulate_fix ignored an "unknown token" and "verified" a set nobody had
     proposed;
   * it called `owners` on a secret and a role (`'org_a:secret:00008' is not an
     Asset or DataStore`), two wasted turns.

   Proving a set is not a judgement call, so the run now proves both and the
   model chooses between two verified options.

Result on org_a v1, same model:

| | S4 (`216fc89472eb`) | S5 (`728d232b2390`) |
|---|---:|---:|
| input tokens | 60,777 | 25,752 (**-58%**) |
| LLM calls | 12 | 7 |
| wall time | 81 s | 28 s |
| fix plan | 7 fixes, verified | 7 fixes, verified |

**Is the triage decision unchanged?** Measured properly, on the same graph with
the same stub model (`tests/test_token_trim.py`, S4 baseline measured with the
S4 code at commit `2637d6f`): the fix set and the final verdict on **all 24
findings** are identical, as are the suppressed, expired and deprioritised
lists, with input tokens 35,487 -> 13,934 (-61%, 11 -> 6 model calls). One thing
changed on purpose: Triage's list now names only the Internet-facing
candidates. The three internal hops (db host, privesc) are still ranked by the
Pathfinder and get the same verdicts.
With the real model the visible difference is that it now investigates all 9
entries (S4 saw 6) and notices the live acceptance it used to miss: both are
corrections, not regressions.

One more grounding rule came out of the real runs. The model once left out the
finding whose risk acceptance had **expired**, which is exactly the finding
that is back in scope. Now a candidate that nothing suppresses and memory did
not carry is always investigated. The model orders the list but cannot drop an
entry (`added_by_rule` in the Triage output).

## 2. Three kinds of memory, each changing a real decision

S03 put memory in the graph; S05 makes the next run *behave differently*
because of it. The three kinds are the psychologist's split, and the
difference matters because each is recalled differently.

### Episodic: "what happened last time" -> do not redo it

Episodic memory is a record of specific events: this run decided *schedule* on
this finding, on this date, for this reason. It answers "have we been here
before?".

**The behaviour.** Before the Triage model reasons at all, the run recalls
memory for every finding it is about to show it (`triage_memory`, by="run";
the trace has the `carried_verdicts` step *before* Triage's first LLM call).
A candidate whose newest verdict still stands is **carried**: it keeps that
verdict and is not investigated again. It stands unless something changed for
it:

* it is on a NEW or cost-changed crown path (the Sentinel's drift),
* a learned pattern flagged it on arrival,
* or a risk acceptance on it **lapsed after** that verdict was made (one that had
  already expired is part of what the verdict decided).

That is a rule, like suppression (a fact, not the model's opinion). The model only
sees what is left to decide.

**In our runs.** On v2 (`org_a_v2:run:8c275ddaab63`), with v1's memory present:
**8 candidates carried**, each starting from v1's verdict, and **1 investigated**:
the new path's entry. The same memory feeds two more savings. The Fixer reuses
v1's owner routing for 5 of the 6 fix assets (`remembered_routes`; the on-call
slot `2024-01-01/2024-01-08` still covers the v2 clock, 2024-01-07, otherwise it
looks the pager up again), and looks up only the new host. When *every*
candidate is carried, the Pathfinder skips its model call entirely and ranks
from the paths alone (`skipped_llm`).

### Semantic: "what is generally true" -> flag it on arrival

Semantic memory is a generalisation, detached from the event that taught it:
*"tomcat 10.1.8 is how attackers get in here"*. It answers "what does this
remind me of?".

**The behaviour.** At the end of a run the Reporter turns what it saw into
patterns: every software image (CPE) that was the way in on a crown-jewel path
becomes a `Pattern {kind: "crown_path_image"}` ABOUT those `Software` nodes. On
the next scan, the **Sentinel** checks the *arriving* findings against memory
(`triage_memory` matches a Pattern to a finding through the same asset, the
same CPE, or the same CVE) **before it computes a single path**.

**In our runs.** v1 learned `org_a:pattern:de324eaa4cbc`: "Image apache tomcat
10.1.8 was the way in on 4 crown-jewel path entries in scan v1". In v2, 14
findings arrive. The Sentinel flags 06879 (the new path's entry host,
`vireo-basalt-edge-192`, built from tomcat 10.1.8) at trace step 4
(`pattern_flags`). The path diff runs at step 5. Triage then investigates 06879 first, marked
`flagged_by: org_a:pattern:de324eaa4cbc`. The flag also caught 06868, another
arrival on that image that turns out to be on no crown path. A pattern is a
reason to look, and the path search is the verdict, which is why the flag
never skips the search.

### Procedural: "how we handle this" -> change the rule, keep the history

Procedural memory is know-how: the playbook. It answers "what do we do with a
T1190 on the edge?". It changes when a human says "no, not like that".

**The behaviour.** `make verdict RUN=... FINDING=... DECISION=reject REASON="..."`
records an analyst Verdict (REVIEWS the agent's verdict). If the reason is
*reusable* (a rule, not "this host is decommissioned on Friday": see
`memory.is_reusable`), it becomes a **new Playbook version** for the finding's
technique: the body gains the rule as a numbered step, and `policy` gains a
machine-readable `{when: {from_internet, on_crown_path, kev}, decision,
instead_of}`. The old version stays, `SUPERSEDES`-linked. The next run's
Reporter applies every rule in force at its clock to its verdicts.

**In our runs.** v1 decided `schedule` on 06857 (Ghostcat, KEV, Internet-facing,
on a crown-jewel path, but cut further in by the shared CI runner fix). The
analyst rejected it: *"A KEV exploit on an Internet-facing host on a crown-jewel
path gets patched now, even when the cut is further in: one funnel fix is a
single point of failure."* That wrote `org_a:playbook:T1190:v3` (SUPERSEDES v2,
which SUPERSEDES v1). On v2 the playbook in force is v3, and 06857 is
**fix_now** with `playbook: org_a:playbook:T1190:v3`, while its non-KEV
neighbours 06858 / 06859 stay `schedule`: the rule generalised on the facts,
not on the id.

**Time, again.** The analyst's verdict and the playbook are stamped on the
synthetic clock, one hour after the run's scan. A run of a *later* scan sees
them. A re-run "as of" the original scan time sees memory as it was then: the
S04 `as_of` rule, now applied to procedural memory.

### Why memory moves between scans at all

Our two scans live in two graphs (`org_a`, `org_a_v2`) so they can be diffed
side by side. Memory belongs to the *org*, not to a scan. So the Sentinel's first
step on a new scan is `MemoryRepo.carry_over`: playbooks (every version), risk
acceptances, verdicts and the triages they hang off, patterns, and earlier runs
with their handoff outputs. These are MERGEd by id and re-attached to the
infrastructure nodes the new scan still has. It is idempotent, and it skips the
step-by-step traces, which stay where they ran. In production there would be one
graph per org and nothing to carry; the cost of our side-by-side setup is one
explicit, tested step.

## 3. Incremental recompute: diff the path sets, don't re-triage

A rescan arrives: 6,855 open findings, 14 new, 21 gone. Re-running the whole
triage answers "what is risky?" from scratch, which is 7 LLM calls to rediscover
that almost nothing changed. The question that matters on a rescan is narrower:
**what changed for an attacker?** That is a graph question with a cheap exact
answer.

`exposure_drift(org, from_scan, to_scan)`:

1. Enumerate every Internet -> crown-jewel walk over `ATTACK_STEP` in each scan
   (the same `(:Internet)-[:ATTACK_STEP*1..8]->(:DataStore {crown_jewel: true})`
   pattern `derive` uses for `:CrownPath`; open findings only, since S3's
   derivation already ignores fixed ones). On org_a that is 9 walks per scan; the
   whole diff, both scans, takes ~70 ms.
2. Key each path by its **node sequence**. Two parallel steps between the same
   two nodes (two exploitable vulns on one host) are one path with two ways to
   walk it, and the cheapest walk is its cost.
3. Diff the two sets:
   * **new**: node sequences only v2 has. Evidence: the nodes and step keys the
     old scan did not have.
   * **closed**: only v1 has. Evidence: the steps that vanished and the findings
     now `fixed`.
   * **cost changed**: same nodes, different min cost (a parallel step came or went).

**"New crown path" precisely:** `new_crown_path` is true iff some node sequence
from the Internet to a crown-jewel DataStore exists in the new scan's attack
layer and not in the old one. A closed path never raises it. A path that got
cheaper or dearer never raises it either: same route, different odds, already
known. A new path through old nodes *does* raise it, because it is a new route.

**The Sentinel** (no LLM) wraps it, in this order, and the trace shows the order:

1. carry memory over;
2. *arrivals*: `exposure_drift(include_paths=false)`, two id reads and **no path
   search**;
3. semantic memory on the arrivals (section 2);
4. the path diff;
5. an `Alert` (Run -[:RAISED]-> Alert -[:CITES]-> Finding, -[:ABOUT]-> Asset)
   **only if** `new_crown_path`.

`make drift ORG=...` on the three orgs: each fires exactly one alert, on the
planted config-change path. Each also reports exactly one closed path (the
patched easy path, evidence `fixed_findings: [org_a:finding:06846]`, ...) and
stays silent about it. org_a: `9 -> 9 paths: 1 new, 1 closed, 0 changed, 8
unchanged`, in 0.7 s including the memory carry-over. A rescan that only fixed
something raises nothing (`test_drift_is_silent_when_a_rescan_only_fixed_things`).

A v2 agent run starts with the Sentinel (a conditional LangGraph edge from
START), and Triage is `BUILT_ON` its `Drift` output. The findings on a new path
are never carried, which is why exactly one thing gets investigated on v2.

## 4. Memory lift is measured, not claimed (Gate B)

`evals/memory_lift.py` runs the same agents on the same rescan twice:

* **cold**: a fresh memory namespace: no earlier runs, verdicts, risk acceptances
  or patterns, only the starter playbooks, and no carry-over;
* **warm**: the memory the agents built triaging v1 (its verdicts, routing and
  learned patterns, plus the risk acceptances), carried in by the Sentinel
  exactly as a normal v2 run does.

What makes it honest:

* **Fresh namespaced graphs** (`lift_org_a`, `lift_org_a_v2`) are built from the
  generator with the seed/scale `make seed` uses: same infrastructure, and the
  demo graphs are never touched.
* **Cold and warm use the same v2 graph**, and memory is reset before each, so
  warm cannot benefit from cold's run, only from v1's.
* **Same model, budgets and prompts.** The only variable is memory.
* **The same correctness bar, checked outside the agents.** `simulate_fix` on
  each final fix set must disconnect every crown jewel, and the set's size must
  equal the oracle's minimum cut for v2 (`labels_v2.json`).
* Gate B passes only if warm does strictly less work (fewer findings
  investigated, or fewer calls, and never more of either) **and** both fix sets
  are correct.

The latest real run is in `evals/results/memory_lift.md` (table copied in section 7).

`make seed` drops and reloads every graph (and any `lift_*` / `scratch__*`
leftovers), so agent memory goes back to the small synthetic seed; `make
reset-memory` and the eval's reset go further, down to the starter playbooks.
Cold means cold.

## 5. Event streaming with SSE, and why the stream reads the trace

**SSE in one paragraph.** Server-Sent Events is one long HTTP response with
`Content-Type: text/event-stream`. The server writes blocks like

```
id: 17
event: tool_called
data: {"seq":17,"agent":"pathfinder","tool":"why_step","ms":21.4,"queries":[{"cypher":"MATCH ...","ms":9.8}]}

```

separated by a blank line. It is one-way (server to client), plain text, and
works through proxies. The browser's `EventSource` reconnects by itself and
sends `Last-Event-ID`, so the server can resume where it stopped. We need no more
than that: the UI watches, and it talks back through ordinary POSTs (verdicts).

**The endpoints.**

| | |
|---|---|
| `POST /runs {org, scan, fake?, cold?}` | creates the Run node, starts the agents in a background thread, returns `run_id` (202) |
| `GET /runs/{id}/stream` | SSE: `agent_entered`, `tool_called` (Cypher + timing from the tool's query log), `llm_called`, `memory`, `drift_checked`, `alert_raised`, `triage_done`, `path_found`, `finding_ranked`, `fix_chosen`, `report_written`, and finally `report_ready` (or `run_failed`) |
| `GET /runs/{id}` | the finished run from the graph: run props, every output, the trace |
| `GET /runs/{id}/events` | the same events as one JSON list |
| `POST /runs/{id}/verdict` | an analyst's accept/reject (section 2, procedural) |
| `GET /orgs`, `GET /orgs/{org}/drift` | orgs, scans, recent runs, alerts; exposure_drift |

A real sequence (v2, abridged): `agent_entered(sentinel)` · `memory(carry_over)` ·
`tool_called(exposure_drift)` · `tool_called(triage_memory)` · `memory(pattern_flags)` ·
`tool_called(exposure_drift)` · `drift_checked` · `alert_raised` ·
`agent_entered(triage)` · `tool_called(scan_findings)` · `tool_called(triage_memory)` ·
`memory(carried_verdicts)` · `llm_called` · `tool_called(playbooks)` · `llm_called` ·
`triage_done` · `agent_entered(pathfinder)` · ... · `path_found` x9 · `finding_ranked` x14 ·
`agent_entered(fixer)` · `memory(remembered_routes)` · ... · `fix_chosen` ·
`agent_entered(reporter)` · `llm_called` · `memory(playbook_rules_applied)` ·
`memory(patterns_learned)` · `report_written` · `report_ready`.

**Why the stream reads the trace instead of the agents pushing to it.** The
obvious design is a queue: each agent `put()`s events, and the HTTP handler
`get()`s them. We did not do that, for four reasons:

1. **Neither side can block the other.** With a push design, a slow client
   makes a full queue that blocks the agents, or makes them drop events. Here
   the run is a background thread with its own event loop. It writes the
   AgentSteps it writes anyway and never knows a client exists. The stream
   polls `steps_after(run_id, last_seq)` every 250 ms *off* the event loop
   (`asyncio.to_thread`).
2. **Late joiners and reconnects are free.** The trace is durable and ordered
   (`seq`, the `NEXT` chain), so a client that connects after the run finished,
   or drops and reconnects with `Last-Event-ID: 17`, gets exactly what came
   after step 17. A queue forgets.
3. **One source of truth.** What the UI shows is literally what is in the graph:
   the same steps `replay` and `GET /runs/{id}` read. The UI cannot show
   something the record does not have.
4. **Any process can watch.** A run started by the CLI or the eval can be
   streamed by the API, because the stream needs only the graph.

The cost is up to 250 ms of latency and one cheap indexed read per tick per
watcher, which is invisible next to LLM calls that take seconds. Three trace
markers make the stream expressive: `agent` steps (entered), `output` steps
(an output node was written; the stream expands it into `path_found`,
`finding_ranked`, `fix_chosen`), and `memory` steps (what memory did).

The stream ends after the run is final **and** a last read finds no new steps
(the run can write a step between our read and its finish), with `report_ready`
carrying the status, headline, risk and stats.

Auth is the MCP server's scheme: `Authorization: Bearer <key>` or `X-API-Key`,
constant-time compare, `/health` open.

## 6. Two runs on one graph: what contended, and what fixed it

We ran two agent runs at once on the same org graph (threads, each with its own
event loop and its own MCP session) and looked for damage.

**What did not contend: the per-run writes.** FalkorDB executes write queries on
a graph one at a time, each atomically (one writer per graph, many readers).
Everything a run writes is keyed by its own run id: the Run node, its AgentStep
chain (`APPEND_AGENT_STEP` finds *this run's* last step and links the new one),
its ToolOutputs (`<run_id>:out:<sha>`), and its handoff outputs. Two runs
interleave their writes, but no write ever reads or touches the other run's
nodes. Result: both runs complete, `chain_ok` on both (seq 0..n-1, `NEXT` edges
exactly in order), **0** steps owned by two runs, **0** `NEXT` edges crossing runs,
and both runs' verdicts present (`tests/test_concurrency.py`, for v1 and for v2
with the Sentinel). The S4 rule "never a global counter, always key by run"
paid off here.

**What did contend: read-modify-write memory.** Publishing a playbook version
reads the current version (v2) and writes v+1 (v3). Each query is atomic; the
*pair* is not. Eight writers at once, without a lock: several read v2, all of
them try to create v3, and the deterministic id (`<org>:playbook:T1210:v3`)
makes all but one fail with `playbook:T1210:v3 already exists: someone published
v3 first`. In our probe: **3 published, 5 lost**.

**The fix is a short lock around just that pair.** `MemoryRepo.lock()` is a
Redis lock *in the FalkorDB server itself* (`SET key token NX PX 5000`), so it
serialises writers across threads **and** processes (API, CLI, eval). The
release is compare-and-delete in Lua, so a holder whose TTL expired cannot free
someone else's lock. The same eight writers with the lock: **8 published, v5..v12
in order, each SUPERSEDING the one before, 7 lock waits**. Only playbook
versioning takes the lock. Plain CREATE/MERGE writes (verdicts, patterns: MERGE
on a deterministic id) are already safe, and locking them would only serialise
runs for nothing.

## 8. Gotchas we hit (exact error + fix)

* **The old trim lied by omission.** `for_llm` cut `scan_findings` to 6 rows and
  `previously_decided` to 6, so the model "chose" 6 of 9 entries and missed a
  live risk acceptance. Fix: a view designed for the decision (aggregates and
  candidates), not a generic list cut.
* **The model verified a different set than it chose.** It simulated `fewest`,
  answered `cheapest`, and claimed success; another run retyped
  `step:usekey:...` as `org_a:step:usekey:...` (`Unknown tokens ignored`). Fix: a
  protocol check (`verify_mismatch`: one correction nudge) and then the run
  proving both candidate sets itself.
* `Error executing tool owners: 'org_a:secret:00008' is not an Asset or DataStore`:
  the cheapest cut revokes a cloud key, which has no owning asset. Fix:
  `CONTEXT.no_asset_owner` names such fixes, so the model stops looking them up.
* **Agent verdicts flooded `previously_decided`.** After one run, every ranked
  and deprioritised finding had a verdict, so warm Triage asked memory about ~20
  extra findings and spent *more* tokens than cold. Fix: verdicts carry `by`
  (`agent` / `analyst` / none = a person), and only human decisions are listed.
  The candidates' memory is recalled anyway.
* **The S3 invariant "no memory write deletes anything"** became "the only
  deletes are the cold-start reset: one fixed `MATCH (n:<MemoryLabel>) DETACH
  DELETE n` per memory label" (`test_repo_refuses_unknown_orgs_and_foreign_writes`).
* **Seeded ids keep the generator's prefix.** In a copied or namespaced graph
  the starter playbook is still `org_a:playbook:T1210:v1`, so v2 SUPERSEDES that
  id. Tests compare version suffixes, not prefixes.
* **`make seed` did not derive** the attack layer (the README said it did); a fresh
  seed left the Sentinel nothing to diff. Fix: `seed` now runs `reachable_graph
  derive` too.
* **`ruff format .` reformats Python blocks inside Markdown** (it rewrote a snippet
  in `S04.md`, which `make lint` then flagged). Write doc snippets one statement
  per line.
* **Windows MAX_PATH:** a venv created under a deep temp path failed to import
  `litellm` (`ModuleNotFoundError: No module named
  'litellm.proxy.pass_through_endpoints.llm_provider_handlers.typesafe_passthrough_logging_handler'`),
  and `git worktree remove` said `Filename too long`. Fix: keep checkouts and
  venvs on short paths (we ran the S4 baseline from the main venv with the old

## 10. Explain it to a judge

**Q: Show me the agent getting smarter between runs.**
Run v1, then v2. On v1 the agents investigate 9 entry points, explain the hops,
look up every owner, and decide "schedule" on a KEV finding the cut covers
elsewhere. An analyst rejects that decision with a reason. On v2 three things
are different, and each points at the memory node that caused it:
**(episodic)** 8 of the 9 entry points carry their v1 verdict and are not
re-investigated; owner routing comes from v1 for 5 of 6 assets. **(semantic)**
the one new entry point was flagged on arrival, before any path search, because
v1 learned "tomcat 10.1.8 is the way in here" (`org_a:pattern:de324eaa4cbc`).
**(procedural)** the KEV finding is now fix_now, citing `T1190:v3`, the playbook
version the analyst's verdict wrote; v2 and v1 of that playbook are still in
the graph. Gate B puts numbers on it: 9 -> 1 findings investigated, 27 -> 15 tool
calls, the same verified, minimal fix set.

**Q: How do you know the rescan's new attack path is real, and that you would not
cry wolf every week?**
The Sentinel does not ask an LLM. It diffs two exact sets: every Internet ->
crown-jewel path in each scan's attack layer, keyed by node sequence. It alerts
only when a node sequence exists now that did not exist before, and the alert
carries the evidence: the three nodes and four steps that are new, and the
config change that made them. Closed paths and paths that just got more or less
likely are reported, never alerted. On all three orgs it fires on exactly the
one planted config change.

**Q: Isn't "memory" just a cache that makes the agent skip work it should do?**
No, for two reasons. First, memory can only skip work when a rule says nothing
changed: the finding is on no new or changed path, no pattern flagged it, and no
acceptance lapsed since its verdict. Anything that changed is investigated, and
the new path's entry always is. Second, the outcome is checked against the same
bar either way: simulate_fix on a copy of the graph must disconnect every crown
jewel, with a fix set as small as the oracle's minimum cut. Warm passes that bar
with half the tool calls; it is less work for the same correct answer.
