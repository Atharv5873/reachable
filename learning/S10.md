# S10 -- Deploying it: a public HTTPS backend and a Vercel front (for Atharv)

S1-S9 ran on `localhost`. S10 puts the same stack on the internet without
changing what it does: the API, FalkorDB and Postgres on a Hetzner VPS behind
Caddy, the Next.js UI on Vercel, and the demo running in replay mode, so no
model is in the loop when a judge clicks around. The runbook with every command
is `deploy/RUNBOOK.md`.

| prod stack: only Caddy public, pinned images, healthchecks | `deploy/docker-compose.prod.yml` |
| TLS, http->https, SSE flush, key kept out of logs | `deploy/Caddyfile` |

## 1. The topology

```
 browser (any network)
   │  HTTPS, same origin: /api/r/<path>      (no key in the page, ever)
   ▼
 Vercel, fra1 ── Next.js route handler  app/api/r/[...path]/route.ts
   │  allowlist + CSRF check + adds X-API-Key from a server-only env var
   │  HTTPS
   ▼
 VPS 91.98.216.38 (Falkenstein)      public: 80 (-> 308 https), 443      ufw: 22/80/443
 ┌─ docker network ───────────────────────────────────────────────────────────┐
 │ caddy :443  Let's Encrypt cert, reverse_proxy, flush_interval -1          │
 │   └─> api :8000  FastAPI: ApiKeyMiddleware, agents, MCP tools in-process  │
 │          ├─> falkordb :6379  graphs + agent memory, AOF on a volume       │
 │          └─> postgres :5432  S7 baseline mirror                           │
 └───────────────────────────────────────────────────────────────────────────┘
          (none of api / falkordb / postgres has a host port)
```

The Vercel function runs in fra1, about 10 ms from the VPS. Every UI call is
browser -> Vercel -> VPS, so the function region matters more than the user's.

## 2. Why the DB ports stay private and the key stays server-side

**DB ports.** FalkorDB speaks the Redis protocol. An exposed Redis port is
found by scanners within minutes (Caddy logged scanner hits seconds after the
certificate was issued). The password is the only thing in the way, and
FalkorDB's `GRAPH.QUERY` can read or delete every graph. So the prod compose
file gives falkordb, postgres and api **no `ports:` at all**. Only Caddy
publishes, on 80/443.

The part that surprises people: **ufw does not protect a published Docker
port.** Docker inserts its own iptables rules (the `DOCKER` chain) ahead of
ufw's, so `ports: "6379:6379"` is reachable from the internet even with
`ufw default deny`. An unpublished port is the only safe database port. The
port scan (`deploy/portscan.py`, run from outside, IPv4 and IPv6) shows 22, 80
and 443 open and 6379/6380/5432/5434/8000-8002/3000/3001 closed.

**The key.** The API key unlocks everything except `/health`: starting
billed runs, writing verdicts, reading every graph. Anything that reaches the
browser is public. So the key lives in one server-only module
(`lib/server/backend.ts`, `import "server-only"`) and in a Vercel env var
without the `NEXT_PUBLIC_` prefix. Next only inlines `NEXT_PUBLIC_` vars into
client code. Two checks prove it: `npm run test:bundle` scans the local
production build (46 files), and `check-live-bundle.mjs` crawls the deployed
site and every `/_next/static` chunk it references (30 responses, about 1 MB).
Neither contains the key or its name. A negative control (a string known to be
in the bundle) makes the scanner fail, so the clean result is meaningful.

The proxy's CSRF guard is what makes a server-side key safe. The route handler
adds the key to *whatever* reaches it, so a POST must be JSON and same-origin
(`Sec-Fetch-Site` / `Origin` vs `Host`). On the live site: cross-site POST 403,
`text/plain` POST 403, same-origin POST 200, a path off the allowlist 404. The
API itself grants CORS to no origin (`API_CORS_ORIGINS=""`). The browser never
calls it directly.

## 3. Vercel cuts long responses: replay from one fetch

A Vercel function has a wall-clock limit (`maxDuration`, 300 s on Hobby), and
the SSE relay is a function. A real run takes 15-70 s, so a stream normally
finishes, but it does not have to: a cold start, a slow model, or a proxy that
buffers can each break it. Two rules make the demo independent of that.

**Replay never streams.** The Investigation screen in replay mode makes one
`GET /runs/{id}/events` and animates the list client-side, waiting each event's
real latency (`ms`, capped at 6 s, divided by the speed). Before S10 that list
stopped at `report_written`. The stream's final `report_ready` was built only
inside the SSE generator, so replay never showed "Report ready". Now
`final_event()` builds it for both, and `/events` ends with it once the run is
final. The Playwright test aborts every `/stream` request and replay still
plays to the end, with zero stream requests made.

**Live streams best-effort, then polls.** The live view still opens an
EventSource. A cut stream reconnects by itself with `Last-Event-ID` (the
backend resumes after that trace step). It switches to polling
`GET /runs/{id}/events?after=<last seq>` every 2 s when the stream is closed for
good (a non-200, e.g. Vercel's 504), after 3 errors, or after 25 s without an
event (a buffering proxy). Events are deduplicated by the same key either way,
and polling ends at the same `report_ready`. The `?after=` keeps each poll
small. The Playwright test answers `/stream` with a 504 and serves `/events` in
two pages, and the run finishes, having asked only for `after=-1`, then
`after=1`.

What remains: a live run watched through Vercel may switch from "streaming" to
"polling the trace" partway through. That's a 2 s granularity instead of
instant. It is never a missing event.

Measured through Vercel: streaming a finished run gives 200,
`text/event-stream`, first byte in 0.39 s, and the same 61 events as `/events`.

## 4. FalkorDB persistence across restarts

FalkorDB is Redis with a module, so persistence is Redis persistence. The
compose file sets `--appendonly yes --appendfsync everysec` (every write goes
to the AOF, fsynced each second) and mounts a named volume at
**`/var/lib/falkordb/data`**, the image's `FALKORDB_DATA_PATH`. Many examples
mount `/data`, which this image does not use: the container then writes inside
its own layer, and `down` loses everything (S1 found this with
`docker inspect`). Test on the VPS: `./prod.sh restart` (`down` + `up`), then
the smoke test. All six graphs and all four demo runs read back, 21/21. Caddy's
certificate lives on a volume too, or every restart would ask Let's Encrypt
again and hit its rate limit.

Seeding is deterministic (`SEED=42`): the VPS produced the same node counts,
planted paths and min cuts as the laptop (org_a: 18,568 nodes, 9 planted paths,
min cut 7).

## 5. Gotchas

* **CRLF in `.env.prod`.** The example was written on Windows. Compose trims
  `\r` from values, but the populate script's shell read did not:
  `http.client.InvalidURL: URL can't contain control characters.
  'reachable-api.devarv.dev\r'`. Fix: `.gitattributes` pins `deploy/** eol=lf`,
  and `prod.sh` strips `\r` when it reads a value.
* **The key in Caddy's access log.** Caddy logs request headers. It redacts
  `Authorization` and `Cookie` by default, but not a custom header, so every
  `X-API-Key` would have landed in `docker logs`. Fix: a `format filter` that
  deletes `request>headers>X-Api-Key`. Note Go's canonical spelling: `X-Api-Key`,
  not `X-API-Key`.
* **`email {$ACME_EMAIL}` with the variable empty** is a Caddyfile parse error.
  The email line is now commented out (optional).
* **`vercel project add` makes a framework-"Other" project.** The build then
  fails: *The Output Directory "public" is empty*. Fix: `apps/web/vercel.json`
  with `"framework": "nextjs"`.
* **`vercel link` edits files**: it appended `VERCEL_OIDC_TOKEN` to
  `.env.local` (gitignored, harmless) and a second `.env*` to `.gitignore`
  *after* `!.env.example`, which silently re-ignores the example. That change
  was reverted.
* **`vercel env add` from a pipe** raced the ssh that fed it (*missing_value*).
  Redirecting from a short-lived file worked.
* **The headline is CVSS 7.5 now, not 5.0.** S9's tiered data changed the
  top-ranked finding to 06856 (CVSS 7.5, scanner rank about 4,000). The S6 demo
  narration said 5.0 (fixed in S11). Gate C compares the two
  headline cards instead of using a fixed threshold.
* **A desktop-only layout on a phone.** There were no responsive classes at
  all, and the 228 px sidebar took half a phone screen (Drift's memory panel
  ended up off-screen). Now the sidebar is an icon rail below `md` and Drift
  stacks below `lg`. Desktop is unchanged, so the video is unaffected.

## 6. Q&A

**Q: Walk me through what happens when I click a finding on the live site.**
The click only changes the URL (`?f=org_a:finding:06856`). Every screen reads
its selection from there, so nothing is sent yet. The findings screen then
asks for what it shows, e.g. `GET /api/r/runs/<run>/subgraph?finding=...`. That
request goes to *our own origin*, the Vercel deployment, so the browser holds
no key. In Vercel's fra1 region the route handler `app/api/r/[...path]` runs:
it checks the path against an allowlist (anything else is a 404 that never
leaves Vercel), for a POST it checks that the request is JSON and same-origin,
and it adds `X-API-Key` from a server-only env var. It then calls
`https://reachable-api.devarv.dev/runs/.../subgraph` over TLS. On the VPS,
Caddy terminates TLS with its Let's Encrypt certificate, drops the key from its
log line, and proxies to `api:8000` on the private Docker network. FastAPI's
key middleware compares the key in constant time and hands the request to the
view. The view calls the same typed graph tools the agents call over MCP
(`attack_paths`, the min cut, `why_step`). Those run parameterised Cypher on
FalkorDB at `falkordb:6379`, a port that exists only inside that network. The
JSON (Cytoscape nodes and edges, both cuts) comes back the same way: Caddy,
then the Vercel handler, which relays the body and sets `no-store`, then the
browser, which draws the graph. About 1 s from India, most of it the two TLS
hops. Click an edge and the same trip happens for `GET /orgs/org_a/why_step`.
