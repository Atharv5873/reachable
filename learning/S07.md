# S07 -- Does the graph earn its place? Five prioritisers, one oracle (for Atharv)

> **Current numbers (S9, `evals/results/comparison.md`; quote these, not the
> tables below).** reachable: path recall@10 100%, decoys@10 0%, paths cut per
> fix 1.16 (= the oracle's min cut), NDCG@10 1.00 (secondary, with its caveat).
> Best baseline, sql_agent: 10% / 11% / 0.30. smart_score: 0% recall and a decoy
> in every top 10 (33%). vector_rag and severity_sort: 0%. Ablation (org_a v1):
> graph off, path recall 100% -> 0%. This note's own tables are the S7 record,
> kept as history.

Six sessions built a product that says "fix these first, because an attacker can
reach the crown jewel through them". S07 asks the question a judge will ask:
**compared to what?** Teams already sort by CVSS. Better teams use a score with
EPSS and KEV in it. An LLM can read a findings export, or query a database, or
search a vector index. If any of those gets the same answer, FalkorDB is
decoration.

So we rank the **same labelled findings** five ways and grade every ranking
against the oracle (the independent networkx answer key from S1):

| prioritiser | what it is | LLM? |
|---|---|---|
| `severity_sort` | CVSS descending. What most teams do today. | no |
| `smart_score` | 0.30 CVSS/10 + 0.25 EPSS + 0.20 KEV + 0.25 Internet-facing, x0.25 if a WAF-style control mitigates it. The best non-graph practice. | no |
| `vector_rag` | the agent, with semantic search over one text document per finding / asset / secret / identity / data store | yes |
| `sql_agent` | the agent, with read-only text-to-SQL over the Postgres mirror | yes |
| `reachable` | the agent, with the FalkorDB tools over MCP | yes |

Then the **ablation**: the reachable agent again, with every graph tool answering
"unavailable". Same prompt, same model, same everything. The difference between
those two rows is the graph, and nothing else.

Code: `packages/eval/src/reachable_eval/` (`store.py` the baselines' door,
`base.py` the interface + deterministic two, `agent.py` the shared LLM loop,
`vector_rag.py`, `sql_agent.py`, `reachable.py`, `scoring.py` the only reader of
labels, `report.py`, `run.py`, `cli.py`); tests in
`tests/test_eval_scoring.py`, `test_eval_leakage.py`, `test_eval_runs.py`;
results in `evals/results/comparison.md`, `ablation.md` and `raw/`.

## 1. What we measure, and why these metrics fit prioritisation

A prioritiser's output is an **ordered list**. Nobody fixes 6,862 findings; they
fix the top of the list this sprint. So every metric looks at the **top K**
(K = 10 here: about what a team patches in a week) and asks how good that prefix is.

The answer key gives every finding a relevance, `finding_priority` in 0..1: for
every Internet -> crown-jewel path the finding's step lies on, add the target's
sensitivity weight (crown = 1.0), then scale so the best finding is 1.0. In
org_a that is 14 findings out of 6,862; every other finding is 0.

**Top-K precision (P@K)** is the share of the top K that is relevant at all:
"of the ten things you told me to fix, how many actually stop an attacker?". It is
blunt on purpose: a finding on three paths and a finding on one count the same.
Its ceiling is min(K, #relevant)/K, so org_b (7 relevant findings) tops out at 70%.

**NDCG@K** (normalised discounted cumulative gain) adds the two things precision
ignores, *how* relevant and *where in the list*:

```
DCG@K  = sum over positions i = 1..K of  relevance(i) / log2(i + 1)
NDCG@K = DCG@K of your order / DCG@K of the ideal order
```

The `log2(i + 1)` discount says position 1 matters most (divide by 1), position 2
a bit less (1.58), position 10 much less (3.46). The ideal order (the oracle's
own) scores 1.0, so NDCG is "how much of the achievable value the top of your
list captures". A list with the 1.0 finding at #1 beats the same set with it at
#9. That is the right shape for a queue that is worked from the top.

A hand-checked example (`test_ndcg_matches_hand_calculation`): relevances
a = 1.0, b = c = 0.5, order d, a, e, c, b. DCG@3 = 0 + 1/log2(3) + 0 = 0.631;
the ideal top 3 (a, b, c) gives 1 + 0.5/1.585 + 0.5/2 = 1.565; NDCG@3 = 0.403.

**Attack-path recall@K** is the security question in its plainest form: of the
planted paths, how many have at least one of their findings in your top K?
Fixing any exploit step on a path breaks that path, so a path "represented" in
the top K is a path this week's work can close. (S7 added the fix token to every
hop in `labels.json` so this can be computed from the label file alone.)

**Decoys@K** counts the three planted traps (a CVSS >= 9 KEV vuln with no route,
an exposed critical a WAF blocks, an exposed exploitable host that leads
nowhere) in the top K. Lower is better. A decoy in your top 10 is a week spent
on something an attacker can't use.

**Fix efficiency** takes the prioritiser's own fix set (or, if it has none, its
top M findings with M = the oracle min-cut size) and counts the planted paths it
cuts, per fix, against the oracle's minimum cut, which cuts every path with the
fewest fixes.

**Cost and latency**: model calls, tokens, dollars (LiteLLM's price map) and
wall time per run. The deterministic two cost nothing; the comparison has to say so.

## 2. Why smart_score is the baseline to beat, and what it cannot see

Beating raw CVSS proves little. CVSS rates how bad a vuln *could* be in the
abstract; it knows nothing about this org. Thousands of findings share 9.8.

`smart_score` is what a careful team does without a graph: CVSS for severity,
**EPSS** (FIRST's probability of exploitation in the next 30 days), **KEV**
(CISA's list of vulns exploited in the wild), whether the finding's own host
**faces the Internet**, and a discount when a compensating control (the WAF)
is recorded against it. The weights were fixed before any result existed and
never tuned on the labels (tuning a baseline on the answer key would be
leakage in the baseline's favour; tuning it *after* seeing it lose would be
leakage in ours).

What it structurally cannot see is anything **two hops away**:

* a finding on an *internal* host (the CI runner every planted shared-runner path
  funnels through, org_a's priority-1.0 finding) gets no exposure credit, so it
  sinks to rank ~1,900;
* an exposed host that leads **nowhere** (the dead-end decoy) gets full exposure
  credit, so it rises into the top 10;
* the crown jewel itself, and which secrets and roles reach it, never enter the
  score.

Exposure is a property of one node. Reachability is a property of paths. A
score over node properties, however well weighted, can't express "this medium
CVE matters because of where it leads". In our data the Internet-facing load
balancers carry dozens of KEV 9.8 findings that are exploitable and lead
nowhere near the crown jewel; smart_score ranks them first, and that is the right
call for a node-level score. It is the wrong call for this org.

## 3. Why vector RAG fails on reachability: similarity is not connectivity

The vector baseline is not a strawman. Its documents carry the **one-hop facts**:
an asset's document lists what it can reach, the secrets it holds, the roles it
assumes; a secret's document says what it unlocks; the crown jewel's document
says which secrets unlock it. The model can search as often as the budget allows
(k = 12 per query, up to 15), with the same 24 tool calls the graph agent gets.

What retrieval returns is the documents **most similar to the query text**.
"crown jewel bucket" retrieves the bucket's document and other documents that
*talk like it*, not the ones *connected to it*. To walk a path the model has to
read "unlocked by secret S", search for S, read "stored on host H", search for H,
read "reachable from G", search for G... and each hop is a fresh similarity
search that may or may not surface the right document among 8,600. Four hops
deep, with fan-out at every step, inside 24 calls: the chain breaks, and the
model falls back on what it can see, which is the scanner's list.

The general lesson: embeddings place text by **meaning**; an attack path is a
property of **structure**. Two hosts with near-identical documents can be one hop
from the crown jewel and fifty hops from it. No distance in embedding space
encodes "there is a route from here to there".

## 4. What the ablation isolates, and why it is the cleanest proof

Comparing `reachable` to `vector_rag` changes one thing: the context layer. But
someone can still argue the graph tools are just "a better prompt", or that the
FalkorDB agent wins because of how its tools are worded.

The ablation removes even that. Same agent, same system prompt, same CONTEXT, same
tool **schemas** shown to the model, same model and seeds, same budgets. Only one
thing changes: every FalkorDB call returns `unavailable: the graph store
(FalkorDB) is offline for this run`. If the LLM were doing the work, from its
knowledge of CVEs and its reasoning, the score would barely move. If the graph
is doing the work, the score collapses to what text reasoning over the scanner's
list can do.

It is the software version of a controlled experiment: hold everything constant,
remove one component, measure. "Take FalkorDB out and the product breaks" (Rule 3)
stops being a claim and becomes a row in a table.

## 5. Leakage: how it would silently inflate results, and how we prevent it

Leakage is the baseline (or our agent) seeing the answer, or a proxy for it. It
does not crash anything; it makes a number look better than the method is. Here
is where it could have crept in, and the wall in each place:

| leak | why it would inflate | the wall |
|---|---|---|
| a baseline reads `labels.json` | it would just copy the answer | only `scoring.py` opens labels; an AST test fails if a baseline module imports the scorer or the generator, or names the label file |
| the Postgres mirror's **memory edges** | the synthetic memory holds a verdict ON each decoy ("not reachable") and a risk acceptance on a planted entry: the generator wrote them *from* the ground truth | baselines read `eval_<scan>` views whose `edges` drops every ON edge not from a Finding |
| the **company layer** (ADRs, tickets) | the generator writes an ADR for every planted entry point: "why is this exposed" is correlated with "this is on a path" | the views expose infrastructure tables only; a test lists the view schema |
| a path field in the CONTEXT or a RAG document | `on_crown_path`, `best_likelihood`, `fix_token`... would hand over the graph's answer as text | a test scans the CONTEXT and all ~8.6k documents for every such field name and every planted path's name |
| the role itself | a clever SQL query could read the raw schema | `reachable_eval_ro` has SELECT on the views and nothing else, is read-only, has a 5 s timeout; a test proves `SELECT * FROM <raw>.adrs` is refused |
| tie-breaking by id | planted findings were generated last (highest ids): sorting ties by id would push them up or down for free | ties break on a hash of the id |
| our own agent's memory | `scan_findings` lists `previously_decided` (the same seeded verdicts) | stripped in the reachable toolbox; memory and company tools are not offered |

One leak we **can't** wall off, and say so: the generator gives planted hosts
kinds that background hosts rarely have (11 `web_server` and 2 `db_host` among
1,758 assets in org_a). A text baseline that notices "web_server" gets a hint the
real world would not give. It helps the baselines, not us.

## 6. How the eval is built (so you can defend it)

* **One universe per scan**: the scan's open findings, read from the eval views.
  Every raw output records its size and a hash; the harness refuses a raw file
  ranked over a different set. A test checks the universe equals FalkorDB's open
  findings.
* **The three LLM prioritisers share one loop** (`agent.py`), the product's own
  `run_agent`: primary model only (no fallback to another model mid-matrix),
  temperature 0, provider seeds 1/2/3, one system prompt and job, one CONTEXT
  (the scan counts, the crown jewels, the scanner's own top 25 by CVSS), 6 turns,
  8 model calls, 24 tool calls, every tool result through the same 6,000-char
  `for_llm` trim, the same output schema (`ranked` up to 20 + `fix_set`). A model
  names up to 20 findings; the rest of its order is the same CVSS tail for all three.
* **Grounding**: an id the model names that is not an open finding is dropped and
  counted (`invalid ids`); a fix token must be an open finding or appear in a tool
  result, else it is dropped.
* **vector_rag**: BAAI/bge-small-en-v1.5 (384-d), local ONNX via fastembed, cached
  by text hash; pgvector exact cosine search (no ANN index, so deterministic).
  We tried gemini-embedding-001 first; see the gotchas.
* **sql_agent**: one SELECT per call, 50 rows, 5 s, as the read-only role.
* **reachable**: `scan_findings`, `exposure_surface`, `attack_paths`, `min_cut`,
  `blast_radius`, `choke_points`, `why_step`, `simulate_fix`, `vuln_intel` over MCP.
* **Held-out scan**: the prompts were frozen before the first model run, and the
  only scan looked at while building was org_a v1. The v2 rescans (a week later:
  fixes, new findings, one new path) are the held-out split, reported separately.
* **Reproducible**: `evals/results/raw/<prioritiser>/<scan>_<prioritiser>_s<seed>.json`
  keeps each run's top 100, fix set, whys, cost and tool log; `make eval-score`
  rebuilds every table from those plus the labels, with no model, key or database.
  A rerun of `make eval` skips runs whose raw file exists (the cache), so an
  interrupted matrix resumes.

## 7. What came out, and how to read it

Six scans (three development, three held out), three seeds for each LLM
prioritiser, 66 runs, 254 model calls, $0.50 in all
(`evals/results/comparison.md`):

| prioritiser | NDCG@10 | P@10 | path recall@10 | decoys@10 | paths cut / fix | $ / run |
|---|---|---|---|---|---|---|
| severity_sort | 0.00 | 0% | 0% | 0% | 0.00 | 0 |
| smart_score | 0.00 | 0% | 0% | 33% | 0.00 | 0 |
| vector_rag | 0.04 | 2% | 3% | 0% | 0.14 | 0.011 |
| sql_agent | 0.03 | 2% | 4% | 0% | 0.09 | 0.010 |
| **reachable** | **0.82** | **78%** | **100%** | 0% | **1.09** | 0.006 |
| oracle order | 1.00 | 87% | 96% | 0% | 1.16 | - |

**The zeros are not a bug.** Each org has over 3,000 open findings at CVSS 9.0
or more, and the 14 that matter in org_a are mostly 7.5. A top 10 by CVSS can't
reach them, and a top 10 by CVSS+EPSS+KEV+exposure can't either, since the
Internet-facing 9.8s on the load balancers outscore everything. That is the
product's whole premise, measured: on this data, every node-level ordering puts
the wrong ten things first. smart_score is the only one that also puts a decoy
in, every time. It is the "exposed and exploitable, leads nowhere" trap, which a
node-level score is built to fall for.

**Read the LLM baselines' near-zero as "the model reached for the scanner list".**
vector_rag named 1.7 findings a run and sql_agent 5.2. On the development
scans, 18 of vector_rag's 31 picks were copied straight from the scanner's
top-25-by-CVSS list in the CONTEXT. With no structural tool, a capable model falls back to
the only prioritisation it can see. That is the same failure as severity_sort,
at a cost.

**Held out vs development.** reachable's NDCG@10 is 0.82 on v1 and 0.81 on v2,
with path recall 100% on both. The v2 rescans include one new path that did not
exist when the prompts were written, and it is found every time. No drop on the
held-out split means we did not tune the agent to the scans we looked at.

**Where it falls short of the oracle** (each with a reason in
`evals/comparison_notes.md`). Order inside the top 10: org_a's priority-1.0
funnel finding sits on an internal host and is read late. Under-filling: some
runs name 7 and stop. Fix sets: sometimes the model builds one fix per path
instead of taking min_cut's smaller set. All three are agent-behaviour issues
on top of a correct graph answer: every run represents every path, and every
fix set cuts every path.

**Variance.** Over three seeds, reachable's NDCG@10 ranges 0.79–0.86 and path
recall never leaves 100%. sql_agent swings 0.00–0.08: when a baseline is near
zero, small luck dominates. Temperature 0 plus a provider seed is
*near*-deterministic on Gemini, not bit-exact. That is why we report a spread,
and why `make eval-score` rescoring the saved raw files is the reproducibility
guarantee, not re-running the model.

**The ablation** (`evals/results/ablation.md`, org_a v1, three seeds): graph ON
gives path recall@10 100% and NDCG@10 0.71; graph OFF gives 0% and 0.00. The
same model, prompt and CONTEXT, with only FalkorDB unavailable, finds nothing.

**Leakage**: `tests/test_eval_leakage.py` passes. No baseline module reads
labels or the generator; the views hold infrastructure only; the CONTEXT and all
RAG documents contain no path field and no planted path's name; the read-only
role is refused the raw schema.

**Cost**: reachable is the cheapest LLM prioritiser (~16k tokens, 2.5 calls,
$0.006 a run), because two graph calls answer what the others spend every turn
hunting for. The deterministic baselines are free, and that is the one
column where reachable loses.

## 8. Gotchas (what bit us, so it does not bite you)

* **A free-tier key looks like a paid one until it doesn't.** S6 fired 20
  concurrent calls without a 429, so we assumed headroom. The matrix hit
  `GenerateRequestsPerMinutePerProjectPerModel-FreeTier` (15/min) within a
  minute, then `...PerDay...` (500/day) with 26 runs left, then, once billing was
  switched to prepay, HTTP 402 "prepayment credits are depleted". The fixes that
  stayed: one **shared pacer** across all concurrent runs (`EVAL_RPM`, the waits
  recorded separately from active time so latency is not polluted by queueing),
  and a **degraded run is never scored**: if any model call failed, the run raises
  and writes no raw file, so a quota error can't masquerade as "the baseline
  ranked nothing". The same trap caught Gate B: a re-run during the outage wrote a
  `degraded` result with 0 tokens that still said PASS (the deterministic calls
  alone produce the right fix set). Check `run status`, not just the verdict.
* **Embeddings have their own quota.** gemini-embedding-001's free tier is 100
  documents a minute; 8,600 documents per scan x 6 scans is hours. A local
  384-d model (bge-small via fastembed, ONNX, CPU) embeds a scan in about a
  minute, costs nothing and is deterministic. For a baseline, "a decent
  open embedding" is the fair choice anyway: nobody can say we picked a weak
  hosted one.
* **DDL can't take bind parameters.** `CREATE ROLE ... PASSWORD %s` fails with
  `IndeterminateDatatype: could not determine data type of parameter $1`.
  Postgres plans only DML with parameters; for DDL, compose with
  `psycopg.sql.Literal` / `Identifier`, which quote safely.
* **Concurrent setup races.** Each eval process set a random password for the
  read-only role; the second one locked the first out (`password authentication
  failed for user "reachable_eval_ro"`). The password is now derived (HMAC of the
  admin password), so every process computes the same one.
* **A SQL guard by keyword-list has holes.** "Must start with SELECT or WITH"
  lets `WITH x AS (UPDATE ...) SELECT ...` through. The role being read-only is
  the real wall; the regex is a second one, and a test now tries the data-modifying
  CTE. Defence in depth means each layer is tested on its own.
* **Windows line endings.** Python's text mode writes CRLF on Windows; rewriting
  an LF file that way turns every line into a diff. Open with `newline=""` and keep
  the file's own EOL.
* **Hand calculations drift in the fifth decimal.** One expected NDCG@5 was
  written as 0.66416; the code said 0.66414, and the code was right (we had rounded
  an intermediate log). Assert with a tolerance that matches how you computed the
  expectation, and recompute it rather than "fixing" the code.
* **The oracle's order is not every metric's ceiling.** Sorting by
  `finding_priority` maximises NDCG and P@K by construction, but path recall@10
  can be beaten: a list that spends its ten slots on ten *different* paths covers
  more paths than one that stacks three findings of the same high-value path. We
  label that row "oracle order", not "ceiling".

## 9. Three questions a judge will ask

**Q: How do you know the graph is doing the work and not the LLM?**
A: The ablation. Same agent, same prompt and CONTEXT, same model and seeds, same
tool schemas; only the FalkorDB calls answer "unavailable". On org_a v1, path
recall@10 goes from 100% to 0% and NDCG@10 from 0.71 to 0.00 over three seeds.
The model alone, knowing every CVE and seeing the scanner's top 25, cannot find
one planted path. The relevant findings are mostly CVSS 7.5 (org_a: 12 of 14
are 7.5 or lower), and 3,525 open findings in org_a score 9.0 or more: in text,
nothing marks the 14 that connect to the crown jewel. And the three LLM
prioritisers share one loop, one model and one budget; the only thing that
differs between `reachable` and `sql_agent`/`vector_rag` is the context layer.

**Q: Isn't this rigged? You built the data, the oracle and the winner.**
A: Three things keep it honest. The oracle is a separate networkx implementation
that never touches FalkorDB (S1), so the graph is graded against an answer key it
didn't write. The baselines get every fact the graph has (the same edges, as SQL
rows or as one-hop text), minus the memory and company layers for *everyone*, and
smart_score's weights were fixed before any result. And we report where we lose:
the deterministic baselines are free and instant; reachable's NDCG is ~0.7, not
1.0, because its ordering puts Internet-facing steps before the internal funnel
that sits on three paths. The data is synthetic; we say so, and the generator
artefacts that help the baselines are listed too.

**Q: SQL can do recursive queries. Why couldn't the SQL agent find the paths?**
A: It could in principle: `WITH RECURSIVE` over `edges`, joined to findings,
vulns and controls, with the attack rules (which vuln lets you move, which
secret needs privilege, which control blocks which asset) written into the
recursion. That is reimplementing S2's derivation in one SQL statement, by an
LLM, in six turns, with a 5 s timeout over ~48k edges. In practice the agent
spent its turns learning the schema and sampling rows. That is the point of the
product: the attack semantics live once, in the graph (ATTACK_STEP edges and
typed tools), so the model asks "what reaches the crown jewel?" instead of
deriving it.
