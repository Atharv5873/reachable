# S04 -- The agents: LLMs choosing graph tools, coordinating through the graph (for Atharv)

S01-S03 built a graph that can answer attacker, company and memory questions,
and 13 tools that ask them. S04 puts a team of four agents on top:

    Triage  ->  Pathfinder  ->  Fixer  ->  Reporter

Each one is an LLM that is shown our MCP tools and **chooses which to call**.
FalkorDB still does every piece of real work (paths, cuts, simulations); the
LLM decides what to ask, in what order, and how to explain the answer.

Four rules shape everything below:

1. **Tool selection is the model's.** We never script "call A then B" inside an
   agent. (The scripted, no-LLM version is Gate A, kept as the baseline.)
2. **Agents never touch the graph.** Reads go through MCP tools; writes go
   through `MemoryRepo` (fixed Cypher, memory labels only). No agent sends Cypher.
3. **Handoffs go through the graph.** Each agent writes its output to the org
   graph; the next one reads it back by run id.
4. **Time is explicit.** The data lives on a 2024 clock; the demo runs in 2026.
   Every run carries an `as_of` (the scan's time), never the wall clock.

Code: `packages/agents/src/reachable_agents/` -- `llm.py` (router), `mcp_tools.py`
(MCP -> LLM tools), `runtime.py` (budget, cache, trace), `loop.py` (the
tool-calling loop), `agents.py` (the four agents), `graph.py` (LangGraph),
`report.py`, `fake.py` (stub model for CI), `cli.py`.

## 1. LangGraph: StateGraph, state, nodes, edges

LangGraph models a multi-step program as a graph:

* **State**: one dict that flows through the program. Ours (`RunState` in
  `graph.py`) is deliberately small: `org, scan, graph, run_id, as_of`, the
  budget snapshot, and **pointers** to each agent's output node
  (`outputs = {"Triage": "<node id>", ...}`).
* **Nodes**: functions `state -> partial update`. Each of our four agents is a
  node. It returns e.g. `{"outputs": {"FixPlan": id}, "log": [...]}`.
* **Edges**: which node runs next. Ours are linear:
  `START -> triage -> pathfinder -> fixer -> reporter -> END`. (Branching and
  parallel fan-out are S5: Sentinel/drift, concurrency.)
* **Reducers**: how a node's update merges into the state. `outputs` uses a
  dict-merge reducer, `log` uses list concatenation (`operator.add`), so each
  node adds to them instead of overwriting.

```python
g = StateGraph(RunState)
g.add_node("triage", ...)
g.add_node("pathfinder", ...)  # etc.
g.add_edge(START, "triage")
g.add_edge("triage", "pathfinder")
...
app = g.compile(checkpointer=InMemorySaver())
await app.ainvoke(initial_state, config={"configurable": {"thread_id": run_id}})
```

**Why the state must be serialisable.** A checkpointer saves the state after
every node (keyed by `thread_id`, our run id). That is what makes a run
durable: if the process dies after Pathfinder, you can resume at Fixer from the
checkpoint. You can only checkpoint plain data. So the live objects (the MCP
session, the LLM client, the FalkorDB connection) are **not** in the state:
they live in `RunCtx`, which the node functions close over. The state is
JSON; the sockets are not.

And because the outputs themselves live in FalkorDB, the state is tiny: it
holds ids, not paths and fix plans.

## 2. The tool-calling loop: how the LLM picks an MCP tool

`loop.py`, one agent:

```
messages = [system: rules + this agent's job, user: CONTEXT (the handoff)]
tools    = the MCP schemas for this agent's tools
repeat:
    reply = LLM(messages, tools)
    if reply has tool_calls:            # the MODEL chose these, from the schemas
        for each call: text = RunCtx.call_tool(...)   # -> MCP -> FalkorDB
        append the assistant message and one `tool` message per result
    else:
        parse the JSON answer; done
```

**How the model "selects" a tool.** We send each tool as a JSON schema: name,
description, parameters. Those come straight from the MCP server's
`list_tools()` (`mcp_tools.py`), which in turn come from our Pydantic input
models. The descriptions were written for this moment in S2: each says what
the tool answers, when to use it, and when NOT to ("Do NOT use min_cut to list
every risky finding"). The model reads them and returns a structured
`tool_calls` list; it can return several at once (parallel calls). Real
example from the Fixer on org_a: one turn asked for `simulate_fix`, six
`owners` and six `decision_trail` calls together.

**How results feed back.** Each result goes back as a `tool` message with the
matching `tool_call_id`. The whole conversation is re-sent on the next turn:
that is how the model "remembers" what it saw.

**What the model never sees or chooses.** `org` and `as_of` are removed from
the schemas and filled in by the run. An agent cannot wander to another org
graph, and cannot pick the wrong time. `run_cypher_readonly` is not on any
agent's list.

**Why we still cap the loop.** Because the model chooses, it can also choose
badly: in one real run Gemini's Pathfinder called `exposure_surface`, then
`choke_points`, then `blast_radius`, then `attack_paths` again, one per turn,
until the provider's quota ran out. The loop enforces the protocol, not the
plan:

* a turn cap per agent (Triage 5, Pathfinder 4, Fixer 5, Reporter 1); on the
  last turn `tool_choice="none"` forces an answer;
* a run budget (`max_llm_calls`, `max_tool_calls`), per-tool caps
  (`simulate_fix` once per run: it copies the graph);
* one nudge if the agent tries to finish without a tool its job requires
  (Fixer must have called `simulate_fix`), one retry if the answer isn't JSON;
* a cache: an identical `(tool, params)` call is answered from the run's
  cache and costs nothing.

**The grounding half.** The model's JSON answer is never written as is. Each
agent has a `finalise_*` function that checks every id against the tool
results the run actually received, drops what was made up (listed under
`dropped`), and takes the facts that matter from the tools, not the prose: is
an acceptance live? (`triage_memory`) Did the cut disconnect the crown jewel?
(`simulate_fix`, for exactly the chosen set). If the model never answered
(budget, outage), the same function builds the output from the tool results
alone, so the run still finishes.

**Tool results are data, not instructions.** The system prompt says so; the
results are passed as JSON; and `runtime.py` flags any result whose text looks
like an instruction ("ignore previous instructions", ...) and puts a warning
in front of it. Our data is synthetic, but the discipline is the point.

## 3. Why the handoff goes through a Run node in the graph

The easy way is to pass Python objects from one agent to the next. We don't.
Each agent writes its output through `MemoryRepo.write_output`:

```
(:Run)-[:HAS_OUTPUT]->(:Triage)<-[:BUILT_ON]-(:PathAnalysis)<-[:BUILT_ON]-(:FixPlan)<-[:BUILT_ON]-(:Report)
(:Triage|:PathAnalysis|:FixPlan|:Report)-[:CITES]->(:Finding)
(:Run)-[:HAS_STEP]->(:AgentStep)-[:NEXT]->(:AgentStep)-[:RESULT]->(:ToolOutput)
```

and the next agent **reads it back** with `read_output(run_id, label)`.

* **Durability.** The process can die; the outputs are in FalkorDB (AOF on).
* **Replay.** `python -m reachable_agents replay --run-id ...` re-renders the
  whole run from the graph alone. `runs/<id>.md` is always rendered from the
  read-back, never from in-memory objects: the file is proof the run is
  reconstructable.
* **Coordination (Track 02).** The agents never call each other. They share a
  blackboard: the Run node. A later agent (S5's Sentinel, a human, a second
  Fixer) can join by reading the same nodes. And because outputs `CITE`
  findings, "every run that ever discussed finding X" is one traversal.
* **Memory for next time.** The Reporter writes a `Verdict` per decided
  finding into the same graph `triage_memory` reads, so the next run starts
  from this one's conclusions.

## 4. LiteLLM routing and fallback (and what the free tiers really allow)

`llm.py` builds a LiteLLM `Router` over up to three deployments, in order:

| | model | key |
|---|---|---|
| primary | `gemini/gemini-3.5-flash-lite` (free) | `GEMINI_API_KEY` |
| fallback | `groq/qwen/qwen3.8-27b` (free) | `GROQ_API_KEY` |
| reserve | any small paid model, off unless set | `LLM_RESERVE_MODEL` + `LLM_RESERVE_API_KEY` |

**A 429, step by step.** The call goes to the primary. Gemini answers 429.
The `RetryPolicy` says rate limits get **zero** retries on the same deployment
(retrying spends the quota you don't have), so the Router walks `fallbacks`
and sends the same messages to Groq. After 2 failures in a minute a deployment
is put in cooldown for 30 s, so later calls skip it instead of paying for
another 429. A 503 ("model overloaded") is different: it is usually gone a
second later, so it gets retried before falling back. Each reply records
`served_by`; the run's stats count calls per model and fallbacks. (Seen for
real: Gemini 429, Groq served the next calls, `fallbacks 2` in the trace.)

**What we learned about the free tiers on day one** (this is the reason for
the reserve):

* Gemini's free tier is **20 requests per day, per model**. One run is ~12
  LLM calls. That is one or two runs a day per model; we exhausted 2.5-flash,
  3.5-flash and 3.6-flash in an afternoon of testing.
* Groq's free tier for qwen is **8,000 tokens per minute**: the Fixer's later
  turns (about 8k tokens) cannot fall back there at all.
* Models get retired: `llama-3.3-70b-versatile` returned 404 by October 2026.
  `python -m reachable_agents check` probes every configured model with one
  real tool call before a demo.

So we also: pace calls client-side (5/min), cap each tool result at 6k chars
for the model (the full result stays in the graph), wait 35 s once on a
short-lived 429 (never on a daily quota), turn off Gemini 2.5's hidden
"thinking" (it ate the 2048-token budget and cut the JSON off), and mark a run
`degraded` when an agent had to finish without its model.

**Why a reserve matters for judging week.** Judges will run the demo when
they want, possibly several times, possibly after we have spent the day's
free quota. A small paid model as fallback 2 costs cents per run and turns
"quota exceeded" into "served by reserve". It stays off until both env vars
are set.

## 5. The as_of / synthetic-clock trap

The synthetic data is anchored at `NOW = 2024-01-01`. The demo runs in
October 2026. Anything that says "now" by reading the wall clock gives the
wrong answer:

* the expired risk acceptance (expired 2023-12-12) is expired either way, but
  a run "as of" 2023-12-02 must still see it as **live** and suppress the
  finding;
* "who is on call" picks a rota slot by time: at a 2026 "now" no slot covers
  it (S3 dodged this with a `current` flag; S4 asks by the scan's time);
* a playbook version published after the scan must not apply to the scan.

How we avoid it: each loaded graph has a `(:Scan {version, ts})` node (v1 at
2024-01-01, v2 six days later). A run's `as_of` defaults to that `ts`, is
stored on the Run node, and `RunCtx.call_tool` injects it into every tool that
takes `as_of` (`triage_memory`, `playbooks`, `owners`, `company_query`). The
model never sees or picks it. The Run also stores `started`, the wall-clock
time it executed: two clocks, both explicit.

Tested: `test_as_of_decides_whether_an_acceptance_suppresses` runs the agents
at `expires - 10 days` (the finding is suppressed) and at the scan's time (it
is back in scope, listed under expired acceptances).

## 6. One real AgentStep trace, annotated

From run `org_a:run:216fc89472eb` (org_a, scan v1, all 12 LLM calls served by
gemini-3.5-flash-lite, status complete). Two consecutive steps of the
Pathfinder, read back from the graph:

```json
{ "seq": 6, "kind": "llm", "agent": "pathfinder",
  "served_by": "primary", "model": "gemini/gemini-3.5-flash-lite", "fallback": false,
  "ms": 1516.1, "tokens_in": 1832, "tokens_out": 33,
  "tool_calls": [ { "name": "attack_paths",
                    "arguments": { "k": 10, "target_id": "org_a:ds:00001" } } ] }
```

* `seq 6`: position in the Run's NEXT chain (Triage used 0-5).
* The model read its CONTEXT (the crown jewel id, from the Triage output it
  read back from the graph) and **chose** `attack_paths` with `k=10` and a
  target. Note what it did not send: `org`.

```json
{ "seq": 7, "kind": "tool", "agent": "pathfinder", "tool": "attack_paths",
  "input": { "k": 10, "org": "org_a", "target_id": "org_a:ds:00001" },
  "ms": 27.6, "ok": true, "n_queries": 1, "db_ms": 17.6,
  "summary": "9 path(s) to 1 target(s); most likely (p=0.200, 5 steps): internet -> ember-basalt-edge-183 -> ssh_key -> fjord-falcon-data-403 -> db_password -> bucket",
  "queries": [ { "graph": "org_a", "ms": 17.63,
    "params": { "source": "internet", "target": "org_a:ds:00001", "k": 10, "max_hops": 8 },
    "cypher": "MATCH (s:Internet {id: $source}) MATCH (t:DataStore {id: $target}) CALL algo.SPpaths({sourceNode: s, targetNode: t, relTypes: ['ATTACK_STEP'], weightProp: 'cost', pathCount: $k, maxLen: $max_hops}) YIELD path, pathWeight RETURN t.id AS target, pathWeight, [n IN nodes(path) | {...}] AS nodes, [e IN relationships(path) | {...}] AS steps ORDER BY pathWeight ASC, target" } ],
  "result_ref": "org_a:run:216fc89472eb:out:8d5473b1ae3c07ce" }
```

* `input.org`: filled in by the run, not the model.
* `queries`: the tool's own log, stored on the step: **which Cypher ran, with
  which parameters, how long FalkorDB took** (17.6 ms of the 27.6 ms; the rest
  is MCP + Python). This is `algo.SPpaths` over `ATTACK_STEP` weighted by
  `cost = -ln(likelihood)`: the 10 most likely paths (9 exist).
* `result_ref`: the `ToolOutput` node holding the full result, stored once per
  run per content (`sha256`), so a cache hit points at the same node.

The run node itself records the clock and the totals: `as_of 1704067200`
(2024-01-01), `started` in 2026, 12 LLM calls, 22 tool calls, 60.8k tokens
in / 3.1k out, 81 s wall time.

Browser query to see it (`org_a`):

```cypher
MATCH (r:Run {id: 'org_a:run:216fc89472eb'})-[:HAS_STEP]->(s:AgentStep)
OPTIONAL MATCH (s)-[:RESULT]->(o:ToolOutput)
RETURN s.seq, s.agent, s.kind, coalesce(s.model, s.tool), s.ms, s.db_ms, o.summary
ORDER BY s.seq
```

## 7. How stable is it? (determinism)

Two runs, same model (gemini-3.5-flash-lite), temperature 0, same graph:

* identical: Triage's investigate list (the 6 Internet-facing entry
  findings), the Pathfinder ranking, the tool sequence (except one extra
  `owners` call);
* different: the Fixer picked `fewest` (7 fixes, effort 11) once and
  `cheapest` (7 fixes, effort 8) once. Both verified by `simulate_fix`.

Temperature 0 is not a guarantee with hosted models (and Gemini 3 is
deprecating sampling knobs). So the facts never depend on it: paths, cuts and
verification come from FalkorDB; the model's freedom is in what to ask and how
to explain. We also removed the judgement call that flipped: with an equal
number of fixes, the Fixer now prefers the cheaper set.

## 8. Gotchas we hit (exact error + fix)

* `langchain-mcp-adapters 0.3.2` requires `mcp<2.0.0`; installing it silently
  downgraded mcp 2.3.0 -> 1.30.0 (our server uses the 2.x `MCPServer`). Fix:
  our own 60-line adapter on `mcp.Client`, and `reachable-mcp` pins `mcp>=2.3`.
* `TypeError: RateLimitError.__init__() missing 2 required positional
  arguments` -- the Router deep-copies its model list, and LiteLLM exceptions
  cannot be deep-copied. Fix: mock a 429 with the string
  `mock_response="litellm.RateLimitError"`.
* `GroqException ... The model llama-3.3-70b-versatile does not exist` (404).
  Fix: `qwen/qwen3.8-27b`; `check` command.
* `GenerateRequestsPerDayPerProjectPerModel-FreeTier, limit 20` -- see section 4.
* Gemini 2.5: answers stopped at exactly 2044 output tokens mid-JSON: thinking
  tokens count toward `max_tokens`. Fix: `reasoning_effort="disable"` for 2.5,
  `"low"` for 3.x, `max_tokens` 4096.
* Gemini 3: multi-turn tool calls need the model's thought signatures back.
  Fix: append the provider's raw assistant message (`reply.raw`), never a
  rebuilt one.
* FalkorDB: `WITH e.fix_token AS tok MATCH (f:Finding {id: tok})` took 3.6 s
  (per-row scan, not an index seek); passing ~3k ids as a parameter made the
  tool result 125 KB (it lands in the query log). Fix: two parameter-free
  queries joined in Python, 0.1 s.
* The Reporter's model wrote "Of 9,576 scan findings": a number found nowhere
  in its context. Fix: every number in the headline and claims must appear in
  the data, else the claim is dropped.

## 9. Explain it to a judge

**Q: How do the agents coordinate?**
Through the graph, not through each other. A run is a `Run` node. Each agent
writes its output (Triage, PathAnalysis, FixPlan, Report) onto that node, and
the next agent reads it back by run id; outputs are chained with `BUILT_ON`
and `CITE` the findings they discuss. Every tool call and every model call is
an `AgentStep` in a `NEXT` chain, with the Cypher it ran. So the coordination
record is durable, replayable, and queryable like any other fact in FalkorDB.

**Q: Isn't the LLM just making things up about attack paths?**
It can't make the facts. Paths come from `algo.SPpaths`, the fix set from
`algo.maxFlow`, the proof from `simulate_fix` on a graph copy. The model
chooses which tools to call and writes the explanation; then every id it
names is checked against the tool results, every claim needs evidence that
exists, every number must appear in the data, and unsupported ones are
dropped and listed.

**Q: What happens when the free LLM tier runs out mid-demo?**
The Router falls back (Gemini -> Groq -> an optional paid reserve). If every
model is down, each agent finishes from the tool results it already has, the
run is marked `degraded`, and the fix plan says "NOT verified" rather than
pretending. And `make triage FAKE=1` runs the whole pipeline with a
deterministic stub model and no network.
