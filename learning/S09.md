# S09 -- Making the eval credible (for Atharv)

S08 ended with reachable at NDCG@10 1.00 against our own oracle, and a note that
the number could no longer tell a good ranker from a great one. S09 does not touch
the agents, the derivation or Gate A's logic. It changes the **data** (crown jewels
now have sensitivity tiers) and the **presentation** (the comparison leads with
the metrics that cannot be won by sharing the oracle's definition).

## 1. A saturated metric hides ranker quality

Before S09 every org had **one** crown jewel, so every path had the same target
weight. The oracle's priority for a finding was then just "how many paths does
it lie on": 1.0 for almost every on-path finding, 3.0 for the CI-runner funnel.
In org_a, 13 of the 14 relevant findings tied at the same value.

NDCG only rewards putting higher-relevance items above lower-relevance ones. With
13 ties, *any* order of those 13 is ideal. So NDCG measured one thing: "on a path
or not". A ranker that put the least important on-path finding first scored the
same as one that got it right. That is what "saturated" means: the metric is at
its ceiling for reasons that say nothing about the quality you care about.

The fix is to give the ground truth a real gradient. Each org now has crown jewels
of two or three tiers, and the oracle sums the target's tier weight over a
finding's paths:

```
critical  1.0   customer / payment data (each org's original crown jewel)
high      0.6   internal credentials, source, deploy secrets
medium    0.3   ops / log stores
```

Now org_a's 14 relevant findings take three distinct values (the CI funnel to the
high-tier deploy bucket = 3 x 0.6 = 1.8, a single route to customer data = 1.0, a
single route to the deploy bucket = 0.6), and the order *inside* the top 10 matters.

What did **not** change: reachability. Only the target of some routes' last hop
moved (e.g. the k8s node role now reads the deploy bucket instead of the customer
bucket). The test pins fingerprints of every org's oracle paths and min cut, taken
from the pre-S9 generator with crown-jewel ids normalised: identical, v1 and v2.
Gate A: same recall, same path counts, same min-cut sizes, max flows and sets.

Two honest notes on the data design:

* **The assignment was fixed from each route's story before any eval ran**
  (machine roles read the deploy bucket; a stolen admin SSH key opens the internal
  credentials DB; vendor support lands on the ops share), with one constraint from
  the guardrails: org_a has 14 on-path findings for 9 routes, so a lower tier on a
  route with only one or two findings would push them below rank 10 *of the
  oracle's own order*, making path recall@10 < 100% by definition. That constraint
  is in the code comment next to `ROUTE_TIER`.
* **The ranker's weights are not the oracle's.** `criticality.py` (S8) weights
  critical / high / medium as 1.0 / 0.7 / 0.4; the oracle uses 1.0 / 0.6 / 0.3. We
  left both as they were. Same tier order, different numbers: where they could
  disagree (three medium routes vs one critical: 1.2 > 1.0 for the ranker, 0.9 <
  1.0 for the oracle) the ranker would lose points, and we would report it.

## 2. Why the structural metrics lead

NDCG asks "does your order agree with the oracle's priority?". reachable's ranker
and the oracle *define* priority the same way (paths to crown jewels, weighted by
sensitivity), so agreement is expected. It is still a real check (the two are
computed independently and could disagree if the derivation were wrong), but it is
the weakest evidence we have, and leading with it invites the obvious objection.

The structural metrics ask questions whose answers do not depend on how anyone
weights priority:

* **path recall@10**: did the top 10 cover every planted attack path?
* **decoys@10**: did a CVSS-9.8-but-isolated, a WAF-mitigated or a dead-end finding
  make the top 10?
* **paths cut per fix**: does the fix set cut every path, and with how few fixes,
  against the oracle's min cut?

A reachability-blind method cannot win these by accident: you cannot cover nine
paths without finding them. So `comparison.md` (and the Evals screen) now lead
with these, put NDCG / P@10 in a secondary section with the caveat written next to
the table, and bring the ablation into the headline.

## 3. The circularity point, as you'd say it to a judge

"Our ranker and our ground truth agree by design: both say a finding matters in
proportion to the weighted number of Internet-to-crown-jewel paths it lies on. So a
high NDCG for us is not a discovery, and we don't lead with it. What the eval shows
is that you *need* the paths to get that priority: severity, exploit likelihood,
exposure, semantic search and SQL over the same data all fail to recover it (0-10%
path recall), and our own agent with the graph switched off falls to 0% too. The
graph supplies the answer; the model doesn't."

## 4. Walling the tier off from the baselines

The tier is a property of the data store, legitimately in the graph, and reachable
reads it there (`attack_paths`, `scan_findings`). The baselines read Postgres
through `eval_<scan>` views, which now leave out `datastores.sensitivity`
(`HIDDEN_COLUMNS`); the RAG documents and the SQL schema description dropped it
too. They still see which stores are crown jewels. `test_eval_leakage.py` adds
`sensitivity` to the forbidden fields (columns, CONTEXT, every RAG document) and
proves the read-only role gets `UndefinedColumn` on it while the raw mirror still
has it.

Is that fair to them? It slightly handicaps vector_rag / sql_agent on the order
*inside* their top 10. It cannot explain their path recall: without paths they do
not find the routes in the first place, tier or no tier.

## 5. Gotchas

* **Do not draw from the shared RNG when adding data.** The new crown jewels are
  created lazily, after the decoy stores, and draw no random numbers, so every other
  node and edge id is unchanged. One extra `rng.choice` would have rebuilt the
  whole org and invalidated every before/after comparison.
* **Fingerprint before you change.** The invariance test compares against hashes
  taken from the old generator, not against the new code's own output.
* **Stale raw outputs.** The eval skips a run whose raw file exists. After a data
  change every old raw is wrong (different labels, different baseline inputs), so
  they were deleted, not overwritten one seed at a time.

## 6. Q&A

**Q: Your ranker and your ground truth agree by design, so what does the eval
actually prove?**

A: Two things, neither of which depends on that agreement. First, that the
priority cannot be recovered without reachability: four reachability-blind methods
given the same findings, the same data and (for three of them) the same model and
budget, cover 0-10% of the attack paths in their top 10, and the best of them puts a
decoy in every top 10. Second, that the graph is what supplies it: the ablation runs
our exact agent with the graph tools answering "unavailable" and it drops from 100%
to 0% path recall. The structural metrics (paths covered, decoys avoided, a fix set
that cuts every path at the oracle's minimum) are what we lead with because they
can't be won by sharing a definition. NDCG is there as a consistency check, with
the caveat printed next to it.
