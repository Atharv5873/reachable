# S02 -- The attack layer, max-flow, and tools an agent can trust (for Atharv)

S01 put an org's infrastructure in a graph. S02 makes the graph *answer
questions an attacker would ask*, and does it inside FalkorDB:

1. **Derive** an `ATTACK_STEP` edge layer with one Cypher query per attack rule.
2. **Search** it with FalkorDB's `algo.*` procedures (shortest paths, BFS,
   max-flow, betweenness).
3. **Wrap** each question as a typed, read-only, capped tool, served over MCP.
4. **Grade** the tools against the S1 oracle with no LLM (Gate A: PASS).

Read sections 2 and 4 twice. Section 4 (max-flow / min-cut) is the
intellectual core of the project.

---

## 1. Why materialise an ATTACK_STEP layer at all?

The S1 graph has the *facts*: `EXPOSES`, `CAN_REACH`, `RUNS`, `HAS_VULN`,
`HOLDS`, `UNLOCKS`, `CAN`, `MITIGATES`... An attack path is NOT a path over
those edges. "Internet -> web -> db host" is only an attack step if the db host
runs software with a network-vector vuln, a scanner reported it, the port
matches, and no control mitigates it *on that host*. That is a 6-node pattern
with a negative condition, per hop.

You could try to find attack paths "live" with one giant variable-length query
over all the fact edges. It fails twice:

* **Tractability.** A variable-length pattern can only follow edges, not check
  a 6-node side-condition at every hop. You end up enumerating fact-paths
  (`Asset-RUNS-Software-HAS_VULN-Vuln<-OF-Finding-ON-Asset-CAN_REACH...`) and
  filtering afterwards, which explodes combinatorially. And graph algorithms
  like `algo.SPpaths` or `algo.maxFlow` only take a *relationship type* and a
  *weight property*. They cannot evaluate a rule.
* **Explainability.** If the answer comes out of one opaque query, you can't
  say *why* a hop exists, or which fix removes it.

So we split the work:

```
  facts (S1)  --[ 10 rule queries, run once ]-->  ATTACK_STEP edges (S2)
                                                     |
                     algo.SPpaths / bfs / maxFlow / betweenness run HERE
```

Each `ATTACK_STEP` is a *conclusion* with its reasons attached:

```
(src)-[:ATTACK_STEP {
    key:        "exploit_remote_service|org_a:finding:06847|org_a:asset:01741|org_a:asset:01742",
    rule:       "exploit_remote_service",
    technique:  "T1210",
    likelihood: 0.43,          # from attack_rules.exploit_likelihood
    cost:       0.84,          # -ln(likelihood)
    fix_token:  "org_a:finding:06847",   # fix this and the edge disappears
    because:    [finding, vuln, software]  # node ids that justify it
}]->(dst)
```

Now the hard question ("is there a path?") becomes a plain graph question over
one relationship type. Every hop carries its own proof (`because`) and its own
remedy (`fix_token`). On org_a the layer is 30,620 edges, derived in 0.5 s.

## 2. Cypher deep dive, on OUR derivation queries

All of these live in `packages/graph/src/reachable_graph/derive.py`.

### 2.1 A rule is a MATCH pattern + a MERGE

Here is `exploit_remote_service` (T1210), the biggest rule:

```cypher
MATCH (src:Asset)-[r:CAN_REACH]->(dst:Asset)-[:RUNS]->(s:Software)-[:HAS_VULN]->(v:Vuln),
      (f:Finding)-[:ON]->(dst), (f)-[:OF]->(v)
WHERE v.av IN $network_vectors
  AND (size(s.ports) = 0 OR r.port IN s.ports)
  AND NOT (:Control)-[:MITIGATES {asset: dst.id}]->(v)
WITH DISTINCT src, dst, f.id AS token, v.likelihood AS lk, [f.id, v.id, s.id] AS because
MERGE (src)-[e:ATTACK_STEP {key: $rule + '|' + token + '|' + src.id + '|' + dst.id}]->(dst)
SET e.rule = $rule, e.technique = $technique, e.fix_token = token,
    e.likelihood = lk, e.cost = -log(lk), e.because = because, e.stale = false
RETURN count(e) AS n
```

Read it as English:

* **The MATCH is the rule's precondition, drawn as ASCII art.** Two patterns
  joined by a comma share variables (`dst`, `v`), so together they say: *src can
  reach dst; dst runs software s; s has vuln v; and a Finding f is ON dst and OF
  v* (a scanner actually reported it on this host).
* **WHERE adds the non-structural conditions.** The vector must be network or
  adjacent. The CAN_REACH port must be a port the software listens on (`ports`
  is a list property, `IN` tests membership; an empty list means "unknown", which
  matches anything, same as the oracle).
* **`NOT (pattern)` is a pattern predicate**: "there is no Control that
  MITIGATES v *scoped to this asset*". The inline map `{asset: dst.id}` filters
  the MITIGATES edge by its property. This is how the WAF decoy gets excluded.
* **`WITH DISTINCT` projects and de-duplicates.** Several CAN_REACH edges (two
  ports) can satisfy the pattern for the same (src, dst, finding). We want ONE
  step per (src, dst, finding), so we project exactly the columns that define a
  step and let DISTINCT collapse the rest. `[f.id, v.id, s.id] AS because`
  builds a list literal: the evidence.
* **`MERGE` on a deterministic key makes the query idempotent.** MERGE means
  "match this pattern, or create it". Because the key is a pure function of
  (rule, fix token, src, dst), re-running derive finds the existing edge instead
  of creating a duplicate. `SET` then refreshes the payload.
* **Parameters (`$rule`, `$technique`, `$network_vectors`)** are passed as a
  map, never string-formatted into the query. Injection-safe, and FalkorDB caches
  the plan: the same query text with different parameters reuses it.
* **`-log(lk)`**: FalkorDB's `log` is the natural log. Why we store cost as
  -ln(likelihood) is in section 3.1.

The simpler rules are the same shape with a smaller pattern, e.g. `db_with_password`:

```cypher
MATCH (src:Secret {kind: 'db_password'})-[:UNLOCKS]->(dst:DataStore)
WITH src, dst, 'step:db:' + src.id + ':' + dst.id AS token, $likelihood AS lk,
     [src.id] AS because
MERGE ...   // same tail
```

Here the fix token is a *step token* built by string concatenation, using
exactly the vocabulary the oracle uses (`step:db:<secret>:<datastore>`), so the
two implementations can be compared token-for-token.

### 2.2 The local_privesc fold (no fake state nodes)

The oracle models privilege as an extra state node: `asset -> priv:asset ->
root-owned secret`. We don't put loose "privileged" nodes in the graph. A
privesc is only useful for what it unlocks, so the step lands on the root-owned
Secret itself:

```cypher
MATCH (src:Asset)-[:RUNS]->(s:Software)-[:HAS_VULN]->(v:Vuln),
      (f:Finding)-[:ON]->(src), (f)-[:OF]->(v),
      (src)-[:HOLDS]->(dst:Secret {requires_priv: true})
WHERE v.av = 'LOCAL' AND v.cvss >= $privesc_min_cvss
  AND NOT (:Control)-[:MITIGATES {asset: src.id}]->(v)
WITH DISTINCT src, dst, f.id AS token, v.likelihood * $creds_likelihood AS lk,
     [f.id, v.id, s.id, dst.id] AS because
```

Two oracle hops become one edge. Its likelihood is the product of both
(privesc x creds_in_files), so whole-path likelihoods still match the oracle.
The fix token is the privesc Finding. One honest cost of the fold: the oracle
could also cut that path by removing the root-owned secret
(`step:creds:...`), and a single-token edge can't represent "either fix works".
It never matters on our data (Gate A's min-cut sizes equal the oracle's), but
it is a real modelling difference to know about.

### 2.3 Idempotency and staleness: mark and sweep

"Re-running derive gives the same edges" is easy with MERGE. But what if a
finding gets fixed? Its step must *disappear*. So derive wraps the rules:

```cypher
MATCH ()-[e:ATTACK_STEP]->() SET e.stale = true            // 1. mark everything
...each rule query sets e.stale = false on what it MERGEs... // 2. re-derive
MATCH ()-[e:ATTACK_STEP]->() WHERE e.stale = true DELETE e  // 3. sweep the leftovers
MATCH ()-[e:ATTACK_STEP]->() REMOVE e.stale                 // 4. tidy
```

`make derive` runs everything twice and compares the full edge signature, and
`test_sweep_removes_steps_whose_precondition_vanished` deletes a HOLDS edge and
checks the creds step goes away.

### 2.4 Variable-length paths, and why we cap them

```cypher
MATCH p = (:Internet)-[:ATTACK_STEP*1..8]->(:DataStore {crown_jewel: true})
UNWIND nodes(p) AS n
WITH DISTINCT n
SET n:CrownPath
```

`[:ATTACK_STEP*1..8]` means "a chain of 1 to 8 ATTACK_STEP edges". This query
labels every node that lies on some Internet -> crown-jewel path.

**Why cap at 8 (`HOP_CAP` in attack_rules.py)?** Variable-length matching
enumerates *paths*, not nodes, and the number of paths can grow exponentially
with length. From the Internet, org_a has 117 exploit steps into the edge zone,
and each of those fans out over CAN_REACH (~4 per rule) with several vulns per
host. Uncapped, that is millions of paths. The cap bounds the work. It is also
the definition of "a path" that the oracle, the derivation and the tools share,
so "found" means the same thing everywhere.

**`UNWIND`** turns a list into rows: one row per node on the path. Then
`WITH DISTINCT n` keeps each node once, however many paths it lies on, and
`SET n:CrownPath` adds a label. (We clear the label first, so re-running is clean.)

### 2.5 Reading a GRAPH.PROFILE

`GRAPH.PROFILE` runs the query and reports, per operator, how many records it
produced and how long it took. Read it **bottom-up**: the deepest line runs
first. This is the read half of the `exploit_remote_service` rule on org_a:

```
Aggregate                                   | Records: 1      | 0.09 ms
  Anti Semi Apply                           | Records: 30483  | 0.54 ms   <- NOT (pattern)
    Expand Into (f)->(dst:Asset)            | Records: 30483  | 2.44 ms   <- f ON dst (both bound)
      Conditional Traverse (v)<-(f:Finding) | Records: 30483  | 6.80 ms   <- find the Finding OF v
        Filter                              | Records: 28012  | 9.08 ms   <- v.av IN $network_vectors
          Conditional Traverse (s)->(v:Vuln)| Records: 31218  | 5.71 ms
            Filter                          | Records: 17366  | 10.40 ms  <- port check
              Conditional Traverse (dst)->(s:Software) | Records: 46580 | 7.89 ms
                Conditional Traverse (src)-[r:CAN_REACH]->(dst) | Records: 23043 | 2.58 ms
                  Node By Label Scan (src:Asset) | Records: 1754 | 0.03 ms
    Filter                                  | Records: 0      |           <- the MITIGATES check
      Conditional Traverse (_anon)->(v:Vuln)
        Argument
```

What it tells you:

* It starts from all 1,754 Assets (label scan) and walks CAN_REACH: 23,043 rows.
* The **port filter** is the big pruner: 46,580 (software on reachable hosts)
  -> 17,366. The vector filter trims 31,218 -> 28,012.
* **Expand Into** means both ends are already bound, so it only checks that an
  edge exists between them. That's cheap.
* **Anti Semi Apply** runs the `NOT (...)` sub-pattern once per row and keeps
  rows where it finds nothing. Its right branch produced 0 records: no
  remote-service target in org_a is mitigated (the WAF decoy is an
  *internet-facing* asset, caught by the public-facing rule instead).
* Total ~45 ms for 30k derived steps.

The CrownPath query's plan shows the planner being smart:

```
Aggregate
  Conditional Variable Length Traverse (_anon_0)-[:ATTACK_STEP*1..8]->(_anon_2)
    Filter
      Node By Label Scan (_anon_2:DataStore)
```

It starts from the **DataStore** end (few crown jewels, few predecessors) and
walks backwards, instead of starting from the Internet (huge fan-out). Same
answer either way, wildly different cost.

## 3. The algo.* procedures we use, and their exact FalkorDB signatures

These differ from Neo4j GDS. There is no graph projection step: you pass labels
and relationship types inline, and names are case-sensitive (`algo.maxFlow`,
`algo.bfs`, `algo.SPpaths`).

### 3.1 algo.SPpaths -- the k most likely attack paths  (`attack_paths`)

```cypher
CALL algo.SPpaths({sourceNode: s, targetNode: t, relTypes: ['ATTACK_STEP'],
                   weightProp: 'cost', pathCount: $k, maxLen: $max_hops})
YIELD path, pathWeight, pathCost
```

*What it computes:* the lowest-total-weight paths from s to t. `pathCount: n`
returns up to n paths in increasing weight (k-shortest *simple* paths).
`pathCount: 0` returns only the paths tied for the minimum. Parallel edges are
distinct paths. Float weights work, even though the docs type `pathWeight` as
Integer. We verified all of this on a toy graph before relying on it.

*Why it fits:* attackers take the likeliest route, and a path's likelihood is
the PRODUCT of its step likelihoods. Shortest-path algorithms minimise a SUM.
The bridge is the logarithm:

```
maximise  p1 * p2 * ... * pn
   <=>    minimise  -ln(p1 * p2 * ... * pn)  =  (-ln p1) + (-ln p2) + ... + (-ln pn)
```

So with `cost = -ln(likelihood)` on every edge, the *shortest* path is the *most
likely* path, and `exp(-pathWeight)` gives you the path's likelihood back.
Every cost is positive (likelihood < 1), so the shortest-path algorithm is
valid. Browser query 3 below shows SPpaths' ranking matches a hand-computed
product exactly.

### 3.2 algo.bfs -- blast radius  (`blast_radius`)

```cypher
CALL algo.bfs(start_node, max_depth, 'ATTACK_STEP') YIELD nodes, edges
```

*What it computes:* everything reachable from one node, level by level, up to
max_depth. `nodes` excludes the start node, and `edges` are the BFS tree
edges. If the start has no outgoing step, it yields **no row at all** (not an
empty list), so the tool checks the node exists and returns "reaches 0".
*Why it fits:* "host X is popped, what can they get to?" is literally a
reachability set.

### 3.3 algo.maxFlow -- the minimum fix set  (`min_cut`)

```cypher
CALL algo.maxFlow({sourceNodes: [s], targetNodes: ts,
                   capacityProperty: 'cap', relationshipTypes: ['FLOW']})
YIELD nodes, edges, edgeFlows, maxFlow
```

*What it returns:* the max-flow value, and the edges carrying **positive flow**
with their flow amounts. **It does NOT return the cut.** Multiple sources/sinks
are allowed (it adds a virtual super-source and super-sink). Important: it
**rejects multi-edges** ("relationship type 'X' contains multi-edges; maxFlow
requires a simple adjacency matrix"), so you cannot run it straight on
ATTACK_STEP, which has parallel edges. Section 4 explains how we get the cut.

### 3.4 algo.betweenness -- choke points  (`choke_points`)

```cypher
CALL algo.betweenness({nodeLabels: ['CrownPath'], relationshipTypes: ['ATTACK_STEP'],
                       samplingSize: 100000, samplingSeed: 42})
YIELD node, score
```

*What it computes:* for each node, how many shortest paths between other pairs
pass through it. High score = a broker that many routes funnel through.
*How we make it meaningful:* over the whole ATTACK_STEP layer, the hubs are
background lateral-movement noise that never reaches a crown jewel. So derive
labels the nodes on Internet -> crown paths `:CrownPath`, and we restrict
betweenness to that induced subgraph with `nodeLabels`. A label is the only
filter `algo.*` accepts, so a derived label is how you point it at "the part
that matters". `samplingSize` larger than the node count means exact (no
sampling), and a fixed `samplingSeed` makes runs reproducible.

### 3.5 Read but not used: algo.SSpaths and algo.WCC

`algo.SSpaths` (same config as SPpaths, no target) gives shortest paths from
one source to *everything*. We don't need it, because SPpaths with a target is
what attack_paths asks. `algo.WCC({relationshipTypes: [...]})` yields
`node, componentId` and ignores direction. Attack paths are directional, so
"connected if you ignore direction" would over-claim reachability. Neither
earned a place.

## 4. Max-flow / min-cut: why the cut IS the fix list

### 4.1 The question

There are 6 attack paths to org_a's crown jewel. What is the **smallest set of
fixes** that breaks all of them? Not "the edges with the highest CVSS", but the
provably minimum remediation set.

### 4.2 Flow, intuitively

Picture attacker "water" flowing from the Internet (source) to the crown jewels
(sink). Every edge is a pipe with a capacity. The **max flow** is the most
water you can push through at once. The **max-flow / min-cut theorem** says:
that number equals the smallest total capacity of pipes you must cut to stop
all water. And a max-flow algorithm finds both.

### 4.3 Unit capacity on fix tokens = the cut is a set of fixes

Cutting a *pipe* is not what a defender does. A defender applies a *fix*, and
one fix can remove several attack edges at once (the same vulnerable DB host is
reachable from 3 web servers: 3 ATTACK_STEP edges, 1 finding). So we build a
flow network where **the only cuttable things are fixes**, each costing exactly 1:

```
 for every fix token t:          FixIn(t) ==[cap 1]==> FixOut(t)
 for every step u -[t]-> v:      u --[cap BIG]--> FixIn(t)
                                 FixOut(t) --[cap BIG]--> v
```

```
   web1 --BIG--\                                  /--BIG--> dbhost
                >-- FixIn(f4) ==[1]==> FixOut(f4)
   web2 --BIG--/          (finding f4 on dbhost)
```

Now think about any finite cut. Cutting a BIG edge costs a million, so a
*minimum* cut never does. It only cuts unit gates, and each gate is one fix
token. A gate shared by many steps (f4 above) costs 1 however many steps it
feeds. Therefore:

* **min-cut size = minimum number of fixes**, and
* **max-flow value = that same number** (the theorem), which we use as a
  built-in self-check.

This is node-splitting: a fix is really a *node* with capacity 1, and flow
algorithms only put capacities on edges, so we split the node into in/out with
the capacity on the edge between them. It also has a lovely side effect.
The split graph has no parallel edges, which is exactly what `algo.maxFlow`
demands. derive.py builds this `FLOW` layer (36,078 edges on org_a) right after
the steps.

### 4.4 Recovering the cut: residual reachability

`algo.maxFlow` gives us flows, not the cut. The standard recovery:

1. Build the **residual graph**. For each edge u->v with capacity c and flow f:
   * if f < c there is a **forward** arc u->v (you could push more), and
   * if f > 0 there is a **backward** arc v->u (you could undo flow).
2. **BFS from the source** in the residual graph. Call the reached set S.
3. When flow is maximal, the sink is NOT in S. Every edge from S to not-S is
   saturated, and those edges are a minimum cut. In our network, those are the
   gates `FixIn(t) -> FixOut(t)` with FixIn in S and FixOut outside.

Why not just take "all saturated edges"? Because saturated is not the same as
cut. Two unit gates in series on one path carry 1 unit each, so both are
saturated, but you only need to cut one.
`test_residual_recovery_picks_cut_not_just_saturated_edges` pins exactly this:
residual BFS from the source picks the first gate and stops, because the
forward arc through it is full.

Worked example (the tiny test graph, `tests/tiny_graph.py`):

```
 P1  internet -f1-> web1 -f4-> dbhost -creds-> s1 -db-> ds1
 P2  internet -f2-> web2 -f4-> dbhost -creds-> s1 -db-> ds1
 P3  internet -f1-> web1 -f5-> s2 -ssh-> box -creds-> s3 -db-> ds1

 max flow = 2   (one unit via f2 -> f4 -> ...; one unit via f1 -> f5 -> ...)
 residual BFS from internet: internet -> FixIn(f1), FixIn(f2); both gates are
 full, nothing else is reachable.  S = {internet, FixIn(f1), FixIn(f2)}
 cut = {f1, f2}  -> size 2 == max flow   (self-check passes)
```

Patch f1 and f2 and all three paths die. `simulate_fix` proves it.

**Small optimisation, with a proof:** the residual BFS only needs the
*ancestors* of the targets (we fetch them by reverse BFS, a few index-backed
queries). A node that cannot reach a target in the original graph can never be
on a residual path that matters: forward arcs are original edges, and backward
arcs exist only on edges carrying flow, which lie on source-to-sink paths. So
every node on a useful residual path can reach the sink. We never touch the
30k background steps.

### 4.5 Which minimum cut? (entry vs crown)

Often several minimum cuts exist. With 6 disjoint chains, any one token per
chain works. Residual BFS **from the source** gives the cut *closest to the
Internet* (`prefer="entry"`: patch the way in). Reverse residual BFS **from the
sink** gives the one *closest to the data* (`prefer="crown"`: lock the vault).
networkx's `minimum_cut` (the oracle) happens to return the sink-side one. Gate
A shows `prefer="crown"` reproduces the oracle's labelled cut **exactly** in all
three orgs, and `prefer="entry"` returns a different, equally minimal set (same
size, also proven by simulate_fix). Neither is "the" answer. They are two
correct answers to the same question, and the agent can choose by business
context.

## 5. simulate_fix: why GRAPH.COPY and not tag-and-rollback

To prove a fix we must re-run path search *without* some edges. `algo.SPpaths`
cannot filter edges by property, so "disable" really means DELETE. Options:

* **Tag-and-rollback on the live graph**: delete edges, search, recreate them.
  Concurrent readers would see a half-fixed graph, and a crash mid-way loses
  edges.
* **GRAPH.COPY** to `scratch__<org>__<uuid>`, delete there, search there, drop
  the copy in `finally`. One server-side command: ~0.3 s at scale 1, ~1 s at
  scale 3. The org graph is never written.

We picked COPY: correctness and isolation beat 300 ms. It is the only tool
that writes at all, and the property test enforces that it writes only to
`scratch__*`.

## 6. Why typed MCP tools beat raw text-to-Cypher

Letting an LLM write Cypher against this schema is tempting and fragile:

* **Correctness.** The model would have to re-derive the attack semantics every
  time (ports, mitigation scoping, the privesc fold). The typed tools encode
  them once, and they're tested against an independent oracle.
* **Safety.** Every tool uses `GRAPH.RO_QUERY` (the server rejects writes), a
  timeout, and Pydantic-validated inputs whose bounds *are* the caps (`k <= 25`,
  depth <= 8, rows <= 200). An out-of-range request is rejected before it
  reaches the database.
* **Cost and latency.** Typed tools use the right algorithm and index-friendly
  query shapes (p50 1-70 ms). Generated Cypher tends to write unbounded
  variable-length patterns.
* **Groundedness.** Every result carries `evidence` (node ids, edges with keys,
  paths), and Gate A checks with a separate query that 100% of it exists. An
  agent can cite it, and a judge can click it.
* **Choosability.** The MCP descriptions say when to use each tool *and when
  not to*, so the S4 agent picks tools instead of improvising queries.

`run_cypher_readonly` still exists as a logged escape hatch: read-only,
forced LIMIT, timeout. Its description tells the model it's the last resort.

## 7. FalkorDB gotchas we hit (exact errors + fixes)

1. `algo.maxFlow: relationship type 'E' contains multi-edges; maxFlow requires
   a simple adjacency matrix` -> run it on the node-split FLOW layer, which is
   simple by construction.
2. `'f' not defined` when a `WHERE NOT (pattern)` is followed by a second
   `MATCH` and later clauses use the second MATCH's variables -> put all
   patterns in ONE comma-joined MATCH, then one WHERE.
3. `'e' not defined` for `(f:Finding {id: e.fix_token})` in the same pattern
   that binds `e` -> inline property maps can't reference same-pattern
   variables. Use `WHERE f.id = e.fix_token`.
4. **Silent wrong answer**: after `WITH ... collect()`, `OPTIONAL MATCH ...
   WHERE m.asset = a.id AND bv.av IN $list` dropped matching rows (one predicate
   alone worked). Fix: keep the single predicate in WHERE and move the second
   test into the `CASE` inside `collect()`. A test on the WAF decoy caught it.
5. `UNWIND $ids AS x MATCH (n:Label {id: x})` is **not** an index seek (it
   traverses and filters). `MATCH (n:Label) WHERE n.id IN $ids` is an index
   scan: why_step went 82 -> 8 ms, min_cut 89 -> 21 ms. Relatedly,
   `id(n) IN $list` is a full node scan.
6. `UNWIND ... MATCH (v:Asset) WHERE v.id = x MATCH (u)-[...]->(v)` returned
   **0 rows** (wrong) in a test. We don't use that shape.
7. Per-row `MERGE` of edges in one big query took 23.6 s for the FLOW layer
   (MERGE rescans a node's edges each time). Since the layer is rebuilt from
   scratch, three `WITH DISTINCT ... CREATE` passes do it in ~0.2 s.
8. `algo.bfs` yields no row (not an empty list) when the start node has no
   matching outgoing edge.
9. The Python client's `graph.profile()` drops the per-operator metrics. Use
   `db.connection.execute_command("GRAPH.PROFILE", graph, query)` to see
   `Records produced` and `Execution time`.

## 8. Five FalkorDB Browser queries (http://localhost:3001, graph `org_a`)

Run `make derive` first. All are parameter-free so you can paste them in.

**(1) One attack path, hop by hop (switch to graph view to see it):**
```cypher
MATCH p = (:Internet)-[:ATTACK_STEP*1..8]->(:DataStore {crown_jewel: true})
RETURN [n IN nodes(p) | coalesce(n.hostname, n.kind, n.id)] AS hops,
       [e IN relationships(p) | e.rule] AS rules
LIMIT 2;
```

**(2) Same paths, with the fix that kills each hop and the path likelihood by hand:**
```cypher
MATCH p = (:Internet)-[:ATTACK_STEP*1..8]->(:DataStore {crown_jewel: true})
WITH p, reduce(lk = 1.0, e IN relationships(p) | lk * e.likelihood) AS likelihood
RETURN [e IN relationships(p) | e.fix_token] AS fixes, likelihood
ORDER BY likelihood DESC LIMIT 3;
```
`reduce` folds the list: start at 1.0, multiply in each step's likelihood.

**(3) The same ranking from algo.SPpaths over cost = -ln(likelihood):**
```cypher
MATCH (s:Internet), (t:DataStore {crown_jewel: true})
CALL algo.SPpaths({sourceNode: s, targetNode: t, relTypes: ['ATTACK_STEP'],
                   weightProp: 'cost', pathCount: 3})
YIELD path, pathWeight
RETURN exp(-pathWeight) AS likelihood,
       [n IN nodes(path) | coalesce(n.hostname, n.kind)] AS hops;
```
You should see the likelihoods from (2): 0.1997, 0.0845, 0.0423. Sum of logs =
log of the product, verified live.

**(4) Max flow, and which unit gates carry flow:**
```cypher
MATCH (s:Internet), (t:DataStore {crown_jewel: true})
WITH s, collect(t) AS ts
CALL algo.maxFlow({sourceNodes: [s], targetNodes: ts, capacityProperty: 'cap',
                   relationshipTypes: ['FLOW']})
YIELD edges, edgeFlows, maxFlow
UNWIND range(0, size(edges) - 1) AS i
WITH maxFlow, edges[i] AS e, edgeFlows[i] AS f
WHERE e.cap = 1
RETURN maxFlow, startNode(e).token AS gate, f ORDER BY gate;
```
maxFlow = 6. Every gate on every chain is saturated (flow 1). This is why you
need the residual BFS (section 4.4) to pick *one gate per chain*, not all of them.

**(5) Check a min-cut by hand: remove its fixes, count surviving paths:**
```cypher
MATCH p = (:Internet)-[:ATTACK_STEP*1..8]->(:DataStore {crown_jewel: true})
WHERE none(e IN relationships(p) WHERE e.fix_token IN [
  'step:db:org_a:secret:00001:org_a:ds:00001', 'step:db:org_a:secret:00002:org_a:ds:00001',
  'step:db:org_a:secret:00004:org_a:ds:00001', 'step:db:org_a:secret:00006:org_a:ds:00001',
  'step:read:org_a:ident:00003:org_a:ds:00001', 'step:read:org_a:ident:00005:org_a:ds:00001'])
RETURN count(p) AS paths_left;
```
Returns 0: the crown-side minimum cut kills every path. Drop any one token from
the list and a path comes back. That is what "minimum" means.

## 9. Explain it to a judge

**Q: Why is a CVSS 5.0 ranked above a CVSS 9.8 here?**
Because risk is "can it be used to reach something that matters", not "how bad
is the bug in a vacuum". In org_a, the most likely attack path starts with
**CVE-2002-0936, CVSS 5.0** (EPSS 0.27, not KEV) on an internet-facing web
server. That server has an SSH key lying on it, which unlocks a box in the data
zone holding the password to the crown-jewel data store. End to end, p = 0.20
of reaching the crown jewel, the top path. Meanwhile org_a has three **CVSS 9.8, KEV** findings
that never appear in any path. One sits in an isolated zone (no route in), one
is internet-facing but a WAF control mitigates it on that host
(`exposure_surface` shows it as `blocked_by_control`), and one is exploitable
but a dead end (`blast_radius` from it reaches 0 nodes). A CVSS-sorted scanner
puts those three at the top. Reachable puts the 5.0 at the top and can show the
evidence for every hop (`why_step`).

*S11 note:* this answer ranks by path likelihood, as S2 did. Since S8 the
product ranks by path-criticality (distinct crown paths a finding lies on,
weighted by the target's tier, S9), so the live headline is 06856, a CVSS 7.5 on
the CI runner that three paths funnel through; this 5.0 is #2. The argument is
the same: neither is anywhere near the top of a CVSS sort.

**Q: How do you know the minimum fix set is really minimum, and really works?**
Three independent checks. (1) Max-flow/min-cut theorem: the cut we recover has
exactly `maxFlow` fixes, and the code refuses to answer if those differ.
(2) `simulate_fix` copies the graph, removes every step those fixes enable,
re-runs path search and confirms zero crown jewels reachable. (3) Gate A
compares against an independent networkx oracle: same size in every org, and
the crown-side cut is the identical set.

**Q: Isn't this just a graph you drew to get the answer you wanted?**
Two implementations of one written rule spec (`attack_rules.py`) must agree:
the Cypher derivation and a pure-Python networkx oracle that never touches
FalkorDB. The test suite asserts that the Internet -> crown-jewel path sets are
identical, hop for hop and fix token for fix token, on all three orgs and on
small regenerated variants. Gate A then grades the tools against the oracle's
labels without any LLM: recall 1.0 on easy, medium *and* hard paths, zero decoys
in top paths, 100% evidence validity.

**Q: Why put the attack logic in the database instead of in Python?**
Because then the *database* answers the security questions, at query time,
with its own algorithms. Shortest paths, BFS, max-flow and betweenness all run
inside FalkorDB over the materialised layer, in milliseconds (attack_paths
p50 16-68 ms, min_cut ~20 ms; at 3x scale, 91k attack steps in 130 MB, derived
in 1.8 s). The agent in S4 gets typed, capped, read-only tools with evidence,
not a Python process holding the graph in memory. And because each step is an
edge with `because` and `fix_token`, every answer can be explained and acted on.
