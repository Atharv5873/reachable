## 1. Why path-criticality is the right ranking signal

"What do I fix first?" has a precise answer once you have the paths: **the fix that
closes the most routes to the crown jewels.** A finding on three Internet ->
crown-jewel paths is worth three findings on one path each, because patching it
closes all three at once. So:

```
criticality(f) = sum over the DISTINCT crown-jewel paths f's step lies on
                 of the target's sensitivity weight (crown = 1.0)
```

S7's agent ranked by what it read first, and `scan_findings` listed Internet-facing
steps first. org_a's most important finding (06856, the CI-runner funnel all three
shared-runner paths go through) sits on an **internal** host, so it came 9th, or
not at all. Exposure is a property of one node; criticality is a property of the
paths. That is the whole product thesis, applied to our own ordering.

Ties (most findings lie on exactly one path) are broken in this order, fixed
before the re-run and never adjusted after it:

1. **a route not yet covered** beats a second finding on a route already listed.
   Without this, ties stack on one route and a top 10 can leave a route out. The
   oracle's own order does exactly that on org_a (89% path recall), as S7's table
   showed; we knew that when we chose this rule, and it is a rule about the
   objective (close as many distinct routes as possible), not a fit to labels;
2. the likelier path first (path likelihood x target weight);
3. Internet-facing, as a minor tiebreak (it used to be the primary sort);
4. a **hash** of the id, never the id (planted findings were generated last, so id
   order would leak).

**How it stays label-free.** The input is the list of paths FalkorDB enumerates
at runtime (`MATCH (:Internet)-[:ATTACK_STEP*1..8]->(:DataStore {crown_jewel:
true})`, 0.1 s here) and each target's `sensitivity`. Nothing else. Three walls,
all in `tests/test_eval_leakage.py`:

* every signal module (`criticality.py`, `tools.py`, `agents.py`, the eval's
  `reachable.py`) is parsed: it may not import the scorer, the generator or the
  oracle, and no string in its code may name `labels.json`, `finding_priority`,
  `ground_truth`, `oracle` or `planted`;
* the reachable prioritiser, ranking step and fix set included, is **run with the
  label files unreadable** (`open` and `Path.read_text` raise on any path with
  "labels" in it), and still ranks by the graph and verifies its fix set;
* `crown_paths` and `criticality` joined the forbidden fields: they never appear
  in the CONTEXT or any RAG document the baselines see.

## 2. Why the min-cut set is the default fix plan (better AND simpler)

S7 let the model write its own fix set. Sometimes it wrote one fix per path (6-9
fixes) when `min_cut` had already answered with 5. Every set still cut 100% of the
paths: just more work for the team. In S8 the run adopts `min_cut`'s answer: the
fewest fixes, or the cheapest cut when it has as few (`total_effort` from the S3
effort gates), proved by `simulate_fix` on a copy of the graph. Only if a crown
jewel stayed reachable would the model's own tokens be added and the union proved
again. It never happened (18/18 verified, 0 expanded), and it can't easily: by the
max-flow / min-cut theorem a minimum cut is the smallest set that disconnects the
target, and `min_cut` self-checks that its cut's capacity equals the max flow.

**Better**: provably minimal, so paths cut per fix went 1.09 -> 1.16, exactly the
oracle's. **Simpler**: one deterministic call replaces a judgement the model kept
getting slightly wrong, and the product's Fixer (S5) already worked this way. The
model's job is the part a model is good at: explaining, writing the tickets.

## 3. The truncation was not max_tokens

Diagnose before you fix. "The model named 7 and stopped" smelled like a
truncated completion. The raw files said otherwise: 487-744 output tokens of a
4,096 limit, `stop=final`, valid JSON. In both short runs the model had called
`attack_paths` and `min_cut` but not `scan_findings`, and it named exactly the 7
findings `min_cut` had shown it. It answered with what it had seen. Raising
`max_tokens` would have changed nothing. And it still does it in S8 (5-9 named a
run, 7 in all three org_a_v2 seeds). We did not change the shared prompt (that
would need every baseline re-run to stay fair); the ranking step fills the head
from the graph, so the model's short list no longer costs anything.

## 4. The "degraded run reported as PASS" trap

During S7's API outage Gate B was re-run. Every model call failed, the run
finished with status `degraded` and **0 LLM tokens**, and the gate printed
**PASS**. Why? Gate B's criteria were "warm does less work than cold" and "both
fix sets are correct", and the run's *deterministic* calls (min_cut, simulate_fix)
produce a correct fix set with no model at all. Every criterion was true. The
verdict was a true statement about the tools and said nothing about the agents.

The general shape: **a gate that checks the answer but not the process can pass a
run that never happened.** The fix is a health check every gate runs first
(`reachable_eval/health.py`). A run is healthy only if its status is `complete`,
it has a trace, it used LLM tokens (> 0) when a model was expected, and no tool
answered "unavailable" and no run-made call failed. An unhealthy run makes the
gate **DEGRADED**, which is a failure, whatever the criteria say. Gate A (no
model) checks that the tools answered at all (assets, paths, cuts, a
`simulate_fix` verdict) and now exits non-zero unless PASS. The eval refuses to
score a 0-token or tool-outage run (the graph-off ablation's refusals are the
experiment, so they are exempt). `tests/test_health.py` replays the outage: 0
tokens and every criterion true gives DEGRADED, not PASS.

## 5. Two smaller fixes

* **Rate limiter on by default** (`LLM_RPM=60`). A live run makes ~7 model calls,
  so 60 a minute never slows the demo, but a burst or a runaway loop now waits for
  a slot instead of tripping the provider. Honest limit: pacing prevents 429s; it
  can't prevent a 402 (prepaid credits at zero). That one is the balance. The
  recorded demo replays from the graph and calls no model at all.
* **`test_mcp` isolation.** It used to call the live `org_a`/`org_c`, so a `make
  seed` during the suite could fail it. It now loads its own two graphs at test
  scale, points the in-process MCP server at only those, and restores the server
  after. The suite passes in any order, including straight after an eval.

## 6. Gotchas

* **The oracle's order is not every metric's ceiling** (S7) mattered here: plain
  criticality order would have dropped path recall to 89% on org_a. Read the
  ceiling row before you aim at it.
* **"Too good" needs an explanation, not a celebration.** 1.00 on six scans with
  zero variance is what you get when the ranking signal measures the same thing as
  the relevance labels. Say so up front (section 7), and name what the number can no
  longer tell you: every crown jewel here has the same sensitivity, so the
  weighting is never exercised, and NDCG can't separate a better ranker from this one.
* **Diagnose, then fix.** Three of the six asks came with a guessed cause
  (max_tokens, the prompt). The raw outputs had the real one each time.
* **Mixed line endings.** Many of the repo's files are CRLF. A Python string replace
  that assumes `\n` silently matches nothing; normalise, replace, and write the
  file's own EOL back.

## 7. Explain it to a judge

**Q: Your NDCG went from 0.82 to 1.00. Did you overfit?**

A: No, and here is how you can check. (1) The new signal comes from the graph at
runtime: for each finding, how many distinct Internet -> crown-jewel paths
FalkorDB finds through it, weighted by the target's sensitivity. That is the
definition of "fix this first", so yes, it measures what the answer key measures.
But the answer key is computed by a separate networkx program over the raw
generated data (S1), and ours by FalkorDB over the derived attack graph (S2). They
agree because the derivation is right (Gate A checks it), not because one reads
the other. (2) A test proves nothing in the ranking path imports the scorer or
the generator or names the label file, and it reruns the whole ranking with the
label files unreadable. (3) The held-out v2 scans, which nothing was developed
against and which contain a path that didn't exist when the prompts were written,
went 0.81 -> 1.00 along with v1. (4) Nothing was tuned: the ordering rules were
fixed before the re-run and nothing changed after it. (5) Take the graph away and
it still scores 0. What 1.00 does *not* show is that we would rank as well on a
differently generated estate; that is the honest next test, and the synthetic
data is the limit we state.
